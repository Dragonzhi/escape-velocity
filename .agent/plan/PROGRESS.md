自动切换（瞄准 2D → 发射切 3D → 结算留 3D → 重试回 2D）+ 手动兜底；
③ 方向与快慢靠**沿轨道流动的光点**（用户唯一亲口说过的"奇怪"就是"轨道圈看不出方向与快慢"）；

**这次转向作废的东西**（诚实结算）：L1 的地月局部系（无太阳）、"每关一个新决策"的阶梯、
"只有 L4/L6 有时间轴"、L6 = 逃逸关，以及六关既有的相位/容差/成功率（要在新设计下重解）。

**同时拿到的实验数据**（用户要求，纯测量、未改游戏文件）：
时间压缩 K 1.0 → 0.4 时，弹弓速度增益上限 **4.1% → 10.2%**，但 L4/L6 的发射窗口 159s → 64s、

### 会话 43 · S3.11 六关手感复核：相位重解 + L4/L6 时间轴 + 时间流「按住即走」

> 会话 42 交接清单的第 1 条。**结论先说：六关里有三关的"行星相位"从一开始就是错的**
> —— 它们是照一条**撞进太阳**的设计航线排的，导致"关卡诡异、不知所云"。修完之后
> L5 从 0.2% 变成 17.5%，L3 从 8.6% 变成 42.5%。

#### 1）复核工具（两个新的开发工具，都入库了）

| 工具 | 干什么 |
|---|---|
| `tools/level-phases.mjs` | **相位设计器**：只留太阳做仿真，得到"一族绕日弧线"，解出"行星该摆在哪个相位"（可指定"第 t0* 秒才对齐"）。打印现状相位 vs 最佳相位的**路线数**对比。 |
| `tools/level-play.ps1` | **合成鼠标玩一关**：起引擎 → 进关 → 现读 `View.size` → 按住时间流按钮 → 抓帧 → 打印**本轮**日志（按时间戳过滤）。 |

#### 2）根因：相位是照一条不存在的弧线排的

L3/L4/L5 的相位注释写着"来自设计航线（240° 方向、Δv 35）的穿越角"。实测那条弧线
**peakR 只有 80** —— 它朝太阳飞，直接撞进太阳（半径 28）。于是相位和任何真实航线都对不上：

| 关卡 | 相位（旧 → 新） | 细网格成功率 |
|---|---|---|
| L3 弹弓 | 195.5 / 198 → **89.4 / 89.0** | 8.6% → **42.5%** |
| L5 大巡游 | 195.5 / 203.1 / 209.7 / 216.4 → **89.5 ×4（真连珠）** | **0.2% → 17.5%** |
| L4 窗口 | 315.5 / 288 → **29.3 / 48.2**（= 第 180 秒才对齐） | 1.1% → **8.9%** |

为什么是 89.5°：能依次穿过 105/135/165/195 四个环的那族弧线**接近径向**（θ 沿径向不变），
所以行星必须摆在那条射线上 —— 这也正是真实 Grand Tour 能成立的原因（八十年代四颗巨行星连珠）。

#### 3）逐关改动

- **L5 大巡游**：去掉海王星的**捕获**要求（L5 的新决策是"路线规划"，捕获是 L4 的机制；
  实测叠加会把可行路线砍到 1/5：280 → 60 量级），四站容差放到 **40/50/60/70**（环画在容差半径上，看得见）。
- **L4 窗口**：「正确发射日期」定在**第 180 秒**（12 次「加速」），跨度收到 300 秒。
  为什么是 180：**可行日期带本身有 ~180 秒宽**（方向窗口 ±30° ÷ 木星 0.335°/s），
  答案放得不够远，t0=0 就也是可行解 —— 这一关的教学（"挑时机"）就没了。
- **L6 单程**：改前它只有 `kind:'escape'` —— 朝任何方向猛推就行（32% 可行、270° 方向都算赢）。
  现在 = **综合**：四颗巨行星连珠 → 必须**依次穿过**（chain 40/50/60/70）**并且**飞出 260，
  再加上**时间轴**（前 4 档时机零解）。2.7%，是六关里最难的，也是叙事上最该难的。
  为此 `resolveResult` 加了一条规则：**逃逸关带 chain ⇒ 航线走完 且 越界，两个都要**。
- **L1 出发**：月球环 24 → 30（顺手修了"注释写 18、代码写 24"的不一致），方向窗口 ±12° → ±17°。

#### 4）时间流按钮：点按 → **按住即走**（L4/L6 的 300 秒轴要按住扫）

- 按下即走一步（= 原来的点按语义），停 `WarpHoldDelaySec`(0.3s) 后开始连按，速率 `TimeWarpRate`(40 倍)
  ⇒ 300 秒轴按住约 7.5 秒扫完，松手即停。
- 为此给 `createButton` 加了 `onPressBegan / onPressEnded` 两个钩子（**在它内部注册**，
  外部仍然不碰节点触摸回调 —— AGENTS 硬约束 6），且这两个钩子**不做 0.5 秒防抖**（幂等由调用方保证）。
- **相态守卫**：新增 `coreTimeWarpAllowed(core)`（只有 Aiming / Armed 能改日期）——
  飞行用的是 `tWorld = t0 + flightTime`，飞行途中改 t0 会让行星在**飞行路径底下跳位**。
  单测三条（Aiming/Armed 允许、Flying/Result 禁止）；HUD 侧同一判据 `setTimeEnabled`。

### 会话 39 · 用户三条：重试仍无反应 / 行星模型跳回 t=0 / 滑杆改时间流按钮

#### 1）「重试本关」UI 有反应但界面不变 —— 找到机制并改成状态驱动

上一版只把"面板作用在错误的关卡"修了，但**面板的显隐仍然只由点按驱动** ✗：只要状态被别的东西改了
（切关、视口重建、自动回归序列），就会留下一个"还在屏幕上、但已经没东西可改"的面板，点它当然没反应。
**改成状态驱动**：`onPhase` 里一旦离开 Result 态就把面板收起（状态是唯一事实来源）。
同时 `resultIndex` 让面板只作用在**它显示的那一关**；每次点按都打日志（含当时的 phase），下次可诊断。

**另一个必须记下来的观察**：合成点击在这台引擎上**经常整个丢掉**（实测 6 次点击只有 1 次进入游戏，
日志里连 `tap:` 都没有）—— 这不是按钮逻辑的问题，而是输入事件本身没送到。真机上也可能是同一现象，
所以"有时候点了没反应"未必全是代码的锅；日志里有没有 `tap:` 那一行，就是区分两者的分水岭。

#### 2）行星模型跳回时间 0（物理对、模型错）

根因一行：飞行段用 `core.flightTime` 同步行星，**漏了发射日期**。
`tWorld = core.t0 + core.flightTime`（瞄准段早就是 `t0 + clock`；只有飞行段漏了）。
这也解释了用户观察到的"物理位置对、建模位置回到 0"—— 物理用的是 `t0`，模型用的是 0。

#### 3）日期滑杆 → 加速 / 回退按钮（用户提议，采纳）

用户的判断是对的：**滑杆是"瞬间跳到某个日期"，而这一版的核心是"时间在流"（探测器绕地球待机）**，两者语义打架。
改成右上角两个按钮「◀ 回退」「加速 ▶」，**按一次走 15 秒**（`Config.TimeWarpStep`），读数仍在左上角显示 `发射日期 15 / 359 秒`。
关键取舍：**步进时只走"世界时钟"，探测器自己的轨道相位不动** —— 它在轨道上等着发射窗口（否则快进时探测器会糊成一团）。

（实测：按下去既没视觉反馈也拿不到回调）。改走它自己的 `onTap`（松手触发），这也正是"按一次走一步"该有的语义。

### 会话 36 · 推力剖面落地（coast / brake）+ HUD 两段式开关 + Δv 共享预算

#### 1）物理内核：`SimOptions.brake`

- `Gravity.ts`：`brake = { dv, startStep? }` —— 从 `startStep`（默认 `steps/2`）起，每步沿 **-v̂** 扣固定 Δv。
  用"恒定推力"而不是一次性反向脉冲：① 预测线**后半段变平**（用户要的"前半段加速、后半段减速"）；
  ② 总量只跟步数有关、与帧率无关（确定性不破）；③ 速度到 0 就夹住，不会把探测器推成倒着飞。
- **先写测试再接线**：`GravityTest` 新增 5 条契约断言（dv=0 与不传 brake **逐点一致**；无引力时末速度 = 初速度 − dv；
  距离可精确预测（10→6 的 5 秒 = 45 单位）；反推开始前的轨迹与 coast 逐点一致；过量反推夹在 0）。

#### 2）游戏侧：一次点火怎么花由"剖面"决定

- `Game.burnToMotion(burn, probeVel0, brakeMode, maxSteps)` —— **预测线与真实发射共用的唯一折算**：
  惯性 = 全部 Δv 给点火；刹车 = 点火拿 `BrakeShare`，其余留作 `maxSteps/2` 起的反推段。
  （两边各写一份是这类系统最容易烂的地方 —— 直接抽成函数，谁都别想绕过。）
- HUD：右上角两段式「惯性 / 刹车」，默认惯性；当前选中的一档高亮。
  ⚠️ 为什么是**两个按钮**而不是一个开关：实测一次合成点击会被引擎投递**两次**（鼠标 + 触摸两条路），
  单按钮"取反"会开了又关（净效果 = 点了没反应）。两段式天然幂等：双击同一侧只是把同一状态设两遍。
  顺手给 `Ui.createButton` 加了 0.5 秒防抖（对其它按钮也是保护）。
- `Test/LevelDataTest` 与 `tools/level-sweep.mjs` 都接受刹车剖面：判据是"**任一剖面有解**"（先惯性、再密网格、最后刹车）。

#### 3）实测结论：两种剖面是"两种战术"，不是升级关系

`game/{Config,Gravity,LevelData}.ts` 编成 CommonJS 到临时目录，`Module._resolveFilename` 把 `game/*`
指过去，然后按**同一份数据、同一套公式**在 Node 里扫（`--grid 24x6`、`--t0 24`、`--file 候选.json`、
`--json`）。唯一刻意的重复是 5 行 `resolveResult`（`game/Game.ts` import 了 Dora，Node 跑不了），
权威判定仍是引擎内的 UnitRunner。校准办法：先用它跑**改之前的**六关，结果与引擎基线一致（六关全有解）。

#### 4）施工中补的两处基础设施（不补就干不下去）

- **物理层 `SimOptions.t0`**（提前从 S3.6.4 拿来的两行改动）：`simulate` 从 `t0` 起累加时间，
  `findGoalIndex` 多一个可选 `t0`。没有它，L4 的"换时机才有解"根本没法测。
- **引擎内驱动脚本**：`tools/engine-run.ps1`（起引擎 → /run → 等 phase=done → 读标记 → 打印日志尾 → 停引擎）
  与 `tools/level-shots.ps1`（逐关重启 + enter-request 进关 + GameShot 抓帧 + TGA→PNG）。
  三个**实测坑**（都写进了脚本注释）：① 引擎的工作目录必须是**引擎目录**（用项目目录当 cwd 会去跑项目的
  init.lua、报 `lualib_bundle not found`）；② **冷引擎的 `Content.searchPaths` 是空的**
  （`sp0=nil` ⇒ `Path(nil,...)` 报 "argument 2 is 'nil'"），`UnitRunner`/`GameShot` 因此加了
  「`searchPaths[0]` 上跳一级」+「`Content.writablePath/escape-velocity`」两级兜底和 `Content:addSearchPath(root)`；
  ③ 标记文件必须**在 /run 之前**删 —— 入口一开始就写一次 `phase=running`，在 /run 之后删会把这次写入吃掉，
  而它跑完的第二次写入**不会重新建文件**（实测：等 400 秒也等不到，白等）；④ `GameShot` 里**不能写
  `require("init")`** —— Dora 的全局 require 按 `Content.searchPaths` 找模块，冷引擎的路径里没有项目根，

  `Content:load` + `load` 执行后，日志立刻出现 `[escape-velocity] started: 6 levels`，截图恢复（3302 种颜色）。
  —— 教训：**"探针说没问题"不等于"真的在做那件事"**，要用一条只有真跑起来才会出现的日志去核对。

### 会话 23 · 相机取景改为"按真实投影求解"（S3.1 复核中发现并修复）

### 会话 18 · 交互改为"相对拖动"，并修掉触摸命中框只有左下象限的问题（已修，双证据验收）

**用户新需求（2026-09-24）**：「按哪里都能瞄准；松手才发射；按下的时候预测线回到直飞，拖动才改变方向。」

**这一轮修了两件事**

#### 1）触摸命中框只剩"左下象限" —— "不是按哪里都能瞄"的真因

`createAimInput` 的根节点原本 `anchor=(0.5,0.5)`。节点的**子坐标原点是「位置 − anchor×尺寸」**，
于是整棵子树（含触摸层）被再推走半个屏幕：命中框只剩左下象限 ——
实测坐标可证：view x ≤ ~1012 与 y ≤ ~615 处按下有效，之外**完全无事件**（当时误以为是"多进程注入"问题）。

修复：`root.anchor = Vec2(0, 0)`（父层 `levelLayers[i]` 的子空间是"左下原点绝对像素"，
取 (0,0) 后命中框正好等于整屏，且 `touch.location` 与 `localToOffset` 的假设一致）。

**证据（六点网格实测，每点都重新进关）**

| 按点（view） | 结果 |
|---|---|
| (200,200) 左下 | `began view=199,199 local=199,199` |
| (1800,200) 右下 | `began view=1800,199 local=1800,199` |
| (200,1000) 左上 | `began view=199,1000 local=199,1000` |
| (1800,1000) 右上 | `began view=1800,1000 local=1800,1000` |
| (1012,615) 中心 | `began view=1011,615 local=1011,615` |
| (600,400) 偏左 | `began view=600,430 local=600,430` |

#### 2）瞄准语义改为"相对拖动（虚拟摇杆）"

旧模型：方向 =「探测器 → 手指」，力度 = 按下点到探测器的距离 —— 按下瞬间就已经按距离拿到力度，
方向也由按下点决定，手感与预期不符（用户原话："按下的地方也不是飞行器所在的地方"）。

新模型（手册 §5.7 已同步）：**按下点 = 摇杆零点**；按下瞬间瞄准归零到"直飞"（正对目标、最小力度）；
之后的**位移**决定方向与力度（位移方向 = 发射方向，长度 = 力度，夹紧 min/max）；松手才发射。
实现上复用 `computeAim`：把按下点当作它的 `probeOffset`；程序化缝隙 `handleOffset/handleLocal` 的参数
语义同步改为"相对按下点的位移"。

### 会话 17 · 预测线整体平移半个屏幕：绘制层的坐标空间变了（已修，视觉+单测双验收）

**用户真机反馈**：「线不是从飞行器位置发射出去的；鼠标按下的地方也不是飞行器所在的地方」——
会话 16 修好接线后暴露出来的第二个问题（当时拖动已能响应，只是画错了地方）。

**根因（用标记点实测出来的，不靠推**）**：S2.2 把 2D 层从"直接挂 `Director.ui`"改成"挂 `levelLayers[i]` / `uiLayer` 容器"，
**绘制层的坐标空间随之改变**：

- `project()` 输出 = **中心原点偏移**（+Y 向上）—— 瞄准数学与 `Trajectory` 都按这个约定写；
- 而 `levelLayers[i]`（`size=(W,H)`、`anchor=(0.5,0.5)`、`position=(0,0)`）的实际子空间是 **左下原点绝对像素 [0,W]×[0,H]**。

实测方法：在该层画 (0,0) / (W/2,H/2) / (W/2,H/2-530) 三个标记点后截图 ——
红点落在屏幕左下角、绿点落在正中心、黄点**正好压在探测器模型上**；而探测器投影值本身是 (0,-530)。
结论：预测线被整体平移 (+W/2, +H/2) 半个屏幕 —— 静止时整条线在画面外（截图里根本看不到线），拖动时才出现在错误位置。

### 会话 16 · 真机"进关卡拖不动"的真正根因：瞄准层没接到状态机（已修，已自动验收）

**上一轮的结论是错的，如实纠正**：会话 15 判断为"S2.2 的全屏吞触摸层独占点击"，据此移除了两块全屏底板的
`touch: true` 并加了"隐藏即断触摸"的兜底。那些加固本身是对的（与引擎自身 UI 写法一致），但**不是这次故障的原因**。

**真正的根因**：`init.ts` 在 S2.2 重写时**漏掉了把瞄准层接到状态机的两行**。旧版（`7cb72b0`）里有
`aim.onDrag((a) => game.onAimDrag(a))` 与 `aim.onRelease((a) => game.launch(a.velocity))`，新版没有。
后果：触摸能到达瞄准层，但拖动不更新 `core.aim`（预测线不跟手）、松手也不发射 —— 玩家的感受就是"进关卡拖不动飞行器"。

**怎么找到的（新增能力：合成鼠标输入注入）**：Dora 的 `Touch` 同时代表鼠标点击，用 Win32 合成鼠标事件驱动窗口
即可复现真实触摸路径。先实测几何：`View.size = 2024×1230`（逻辑坐标，UI 用它），窗口客户区 1349×820，
`client_x = view_x·(clientW/2024)`、`client_y = (1230−view_y)·(clientH/1230)`。
随后在 `init.ts` 临时挂一层最顶层监听层（`swallowTouches=false`）记录每次触摸，并在瞄准层回调里打点 ——
一次拖动就同时拿到"事件是否到达"与"瞄准层是否收到"。

**证据（真实日志）**

- 修复前：`[aim] tapBegan enabled=Y nodeTouch=Y view=1011,480` → `[aim] tapEnded enabled=Y dragging=Y`，
  但**没有任何 `phase ->` 变化** —— 触摸到了、状态机没动（接线缺失的指纹）。
- 修复后（干净构建、已移除全部诊断代码）：点选关 `enter L1` → 拖动松手 `phase -> Flying (L1)` →
  `result = missed` / `phase -> Result` → 点「重试本关」`phase -> Aiming (L1)` →
  再拖再发射 `phase -> Flying (L1)` → `result = missed` / `phase -> Result`。

**新增工具（已入库）**：`tools/input-inject/mousectl.ps1` + README（坐标换算、常用点位、回归流程模板）。
