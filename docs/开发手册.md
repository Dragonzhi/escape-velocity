### 手动接管镜头、按钮与配乐（2026-09-29，已实现，持续验收）

3D 飞行保留自动分镜，空白拖动后从当前机位接管并跟随探测器；手动行星/总览聚焦保持玩家角度，切回自动恢复分镜。观察输入独立于规划输入，按钮区域排除，退出关卡关闭；2D 不变。旋转采用选关手感0.22°/0.16°每像素、俯仰16°–75°，暂停及完成后仍可观察。

操作按钮统一72高、图标72宽/文字144宽、间距8；VGNode线条图标与共同状态反馈覆盖主要界面，关卡信息卡保留信息语义。配乐改用yd的CC0 Galactic Temple，独立AudioSource背景播放、循环、音量0.5，记录加载/播放失败，切关/重试/视口重建不叠播。源码与Lua按镜头、按钮、音频分节提交，证据见PROGRESS。

### 交付前时间控制、巡航镜头与音频（2026-09-29，已实现，待引擎验收）

街机档位支持关卡级 `speedMinPow`/`speedMaxPow`，省略时仍分别使用旧默认值0/7。L1–L3 为 -1/0/+1，待机倍率0.25下显示0.025×、0.25×、2.5×；HUD按边界启用按钮，并以暗色呈现禁用态。全屏规划触摸层继续排除时间控制按钮命中区。

3D巡航机位由探测器当前速度向量计算后方视角，角度使用真实帧时长做平滑追随；前视拟合点贴近探测器。近掠分镜仍共同拟合探测器和相遇行星，手动机位与现有0.6秒镜头转场不变。

`game/Sound.ts` 封装 Dora 音频：应用启动时单次循环播放 `Assets/Audio/bgm_galactic_temple.ogg`；按钮共用 `ui_click.wav`，拖动、取消、发射、近掠、目标完成、撞毁分别由输入/状态事件触发音效。加分回调以累计火箭数选择 `star_1/2/3.wav`。音效使用WAV，配乐使用持久AudioSource播放OGG，不增加运行时依赖；重试重置近掠去重状态，不重启配乐。

已新增档位纯逻辑测试，覆盖下限、上限及0.025×/2.5×计算。构建与Lua对照按本节进度记录；若本机Dora仍无法启动，真实触摸、镜头画面及声音需留作引擎更新后的验收。

### 三关目标环与独立得分（2026-09-29，已实现，待引擎验收）

新街机目标通过 `goal` 配置天体、表面高度区间、进入方向和可选逃逸条件；高度换算为实体半径加表面高度。`bonusPoints` 逐点配置 ID、天体偏移或日心公转位置及判定半径。点位是纯提示/计分数据，不进入天体力源、实体碰撞或预测完成状态。L1–L3 用实际固定步长轨迹判定目标与加分，并扫描跨帧区间。

## 3. 技术栈与运行环境

- **引擎**：Dora SSR。游戏运行时由引擎执行；TypeScript 是源码，编译为 Lua 后由引擎执行。
- **入口**：项目根 `init.ts`。
- **模块导入规范**：
  - 引擎 API：`import { ... } from 'Dora';`
  - 本项目模块：斜杠分隔的**项目根相对模块名**，例如 `import { Game } from 'game/Game'` → 解析到 `game/Game.ts`。**不要**写 `./`、`../` 或带 `.ts` 扩展名。
  - 若通过 `requireProjectModule` 加载（测试用），依赖缓存名用点号，例如 `"game.Game"`。
- **不使用**：浏览器 DOM/Canvas、`requestAnimationFrame`、`setTimeout/setInterval`、Node.js 的 `fs/path/process`、npm 包。
- **计时与循环**：`node.schedule((dt) => {...})` 或 `threadLoop`，计时用累加 `dt`。
- **坐标系**：左手系，+X 右、+Y 上。`Director.entry` / `Director.ui` 直接子节点以**屏幕中心**为原点。
- **关键引擎对象（已核实签名）**：

| 对象 | 用途 | 关键成员 |
|---|---|---|
| `Director.entry` | **3D 场景根**（类型为 `View3D`） | `scene`、`stats`、`showAABB`、`shadowMapSize`、`addChild`、`getRayOrigin/getRayDirection/pick`、`setEnvironmentMap`、`setEnvironmentIntensity` |
| `Director.ui` | 2D UI 根（HUD、按钮） | `Node` |
| `Director.pushCamera` | 设置当前相机 | `pushCamera(camera)` |
| `Camera3D` | 3D 相机 | `position`、`target`、`up`、`lookAt(pos, target, up?)` |

## 4. 架构

### 4.1 分层

```
init.ts                 入口：装配 + 关卡选择 ⇄ 单关运行时（惰性建）+ 单一主循环
  ├─ game/Game.ts        顶层状态机（含 LevelSelect）+ 主循环逻辑
  │    ├─ game/Gravity.ts     纯物理：引力积分 + 轨迹推演（可单测，不依赖引擎）
  │    ├─ game/Scene.ts       3D 场景搭建：行星、土星环、探测器、光源
  │    ├─ game/CameraRig.ts   相机跟随与拉远
  │    ├─ game/Projection.ts  自建世界→屏幕投影（纯函数，无引擎依赖）
  │    └─ game/Trajectory.ts  轨迹渲染（预测线 + 真实尾迹）
  ├─ game/LevelData.ts   六关数据 + 目标判定（纯数据 / 纯函数）
  ├─ game/Hud.ts         触屏输入（相对拖动、松手发射）+ 结算面板 + 关卡选择
  │    └─ game/Ui.ts     视图空间 2D 原语：面板 / 居中文字 / 可点按钮
  ├─ game/Progress.ts    解锁进度：夹紧 / 推进（纯函数）+ 存档读写
  └─ game/Config.ts      全局常量、设计尺寸、配色、调参表
```

**分层原则**：

1. `Gravity.ts` 是**纯函数模块**，只依赖数字与 `Vec2`，不碰任何引擎对象 → 可被测试直接调用，也是"预测轨迹 = 真实轨迹"的唯一实现。
2. `Scene/CameraRig/Trajectory` 只负责"把状态画出来"，不改物理状态。
3. `Hud` 只发意图（`onDrag` / `onRelease` 给出瞄准结果，面板按钮给出 `onRetry` / `onBackToSelect` 回调），不直接改游戏状态。
4. `Game` 是唯一持有全局状态机的模块。

### 4.3 顶层状态机

```
Boot → Title(金唱片开场，S3.3) → LevelSelect ⇄ Aiming → Flying → Result → (重试 | LevelSelect)
```

- `LevelSelect / SolarHub`（D5 ✅）：3D 微缩太阳系沙盘（太阳在中心自发光，各大行星携带真实贴图按真实开普勒速度公转）。全息任务图钉锚定在任务最终目的地天体上，显示代号与获得的火箭星级（★/🚀）；点击图钉平滑推镜特写并滑出任务简报卡片（历史原型、载具类型、三项大师挑战、启动任务按钮）；关卡免除硬性通关锁，全部任务去线性化自由开放。
- `Aiming`：全局冻结（D2），玩家拖动瞄准，实时更新预测轨迹。若选定轨道器模式（D8），预测线上高亮显示「制动窗口段（Braking Window）」，提示捕获可行区间。
- `Flying`：按下发射后进入，行星公转流动，探测器发射。飞掠模式（Flyby）全程不可操作；轨道器模式（Orbiter）下探测器逼近目标引力区时自动切入慢动作特写（S3.17），右下角 `[ BRAKE ]` 激活，玩家拥有且仅拥有一次不可撤销点火机会，触发后动态分支重算剩余轨迹。
- `Result`：判定 借力成功 / 轨道捕获成功 / 错过 / 撞毁；结算面板给"重试本关 / 返回沙盘"（D5）。轨道捕获成功时延迟结算，先环绕目标天体平稳公转 1~2 圈伴飞演出。
  **只有 Result 态能返回沙盘**（`coreBackToSelect`）：飞行途中不许“撤退”，
  与“所有决定只能向前”一致 —— 不可撤销就要走完结算。
- **结算四态**（内部值 → 面板大字）：`success` → `借力成功` / `轨道捕获成功`、`missed` → `错过目标 / 飞离逃逸`、
  `crashed` → `信号中断 / 碰撞坠毁`；判定优先级 = 轨道捕获 > 到达目标 > 逃逸达成 > 撞毁 > 错过（`resolveResult`）。
  `Result` 态下「返回沙盘」以**存档**为准刷新全深空火箭总勋章数。
- **相态流转有日志证据**：每次切换打印 `phase -> <相态> (L<关号>)`，选关/进关/结算另有
  `enter L1`、`built L1`、`result = ...`、`unlocked -> N (saved)` —— 真机排查与自动化回归都靠这几行。
- **单一 schedule**：整个游戏只应有一个驱动回调（挂在 `Game` 的根节点上）。不要把更新逻辑分散到多个 `schedule`，同节点二次 `schedule` 会覆盖前者。
  S2.3 的关卡切换仍然是**一个** `threadLoop`：它每帧只驱动“当前激活的那一关”的 `game.update`，
  非激活关卡的 3D 容器 `visible = false`、瞄准输入关闭。

#### 4.3.1 任务进度与三枚火箭评价（D5）

- **去线性化探索**：关卡免除硬性通关锁，全部任务向玩家开放，自由选择出征。

  ⚠️ 可写目录仍为 `Content.writablePath`（`%APPDATA%/IppClub/DoraSSR/`，**不在项目内**）。

## 5. 核心系统设计

### 5.1 物理：把 3D 砍成 2D 平面

- 所有引力计算在**一个平面**内完成（黄道面）。行星视为点质量，引力按平方反比。
- 渲染仍是 3D：相机斜看这个平面，行星是球体，轨迹是发光的线。
- ⚠️ **平面→世界的映射方向（已实测确定，R3 关闭）**：物理平面必须映射到屏幕上
  **沿屏幕竖直方向**（即世界 Z 进深），**不能**沿屏幕水平方向（世界 X）。
  原因：竖屏宽高比 0.5625，横向空间只有纵向的 56%。实测同一相机（dist=30/tilt=45）：
  横向轨道的 `maxNdcX=1.50`（被裁），纵向轨道的 `maxNdcX=0.72` / `maxNdcY=0.65`（完整可见）。
  推荐映射：平面 `(u, v)` → 世界 `(0, v, u)`；相机在 +Y/+Z 方向斜俯视，视线指向 -Z。
  映射常量集中在 `Config.ts`。
- **相机倾角安全区间**：tilt 控制在 **20°–60°**（dist=30 时 maxNdcY 为 0.34–0.74）；
  超过 70° 会贴边（maxNdcY ≥ 0.86），80° 基本出界。
- **相机距离**：竖屏下纵向轨道在 `dist ≥ 25` 即可完整框住；横向轨道需 `dist ≥ 50`。
  这正是 D3“动态跟随拉远”必要的量化依据。

加速度：

```
a(p, t) = Σ_i  GM_i * (q_i(t) - p) / |q_i(t) - p|^3
```

- `q_i(t)` = 行星 i 在时刻 t 的位置（公转，D1）。
- `GM_i` 用"一个数字"表示引力强度，不必对应真实天体质量。
- **不进黑洞**：`|q_i - p|` 小于行星半径 → 判定撞毁，停止积分（见 §5.8）。

积分：**固定时间步**（固定 dt，例如 1/120 秒），半隐式欧拉或 velocity-Verlet。

- 固定步长的意义：**同一个输入每次结果一致**（验收要求"可预测、可学习"）。
- 帧的 `dt` 只用于"推进多少个物理步"，不让物理步长随帧率变化。必要时对一帧最多推进的步数设上限，防止卡顿后跳帧。

### 5.2 引力弹弓（D1 · A 方案）

- 行星在**公转**。引力场随行星移动，探测器从行星**后方**掠过时自然获得净加速，从**前方**掠过自然减速。这是真实弹弓的机制，不需要额外规则。
- **可视化教学**：在行星上画"公转方向箭头 / 尾迹"，让玩家看见"该从哪边抄"。
- 手感调参在 `Config.ts`：行星公转速度要"肉眼可见但不夸张"，`GM_i` 要能产生明显弯曲但仍可规划。
- **原理提示（给玩家的一句话）**：从行星运行方向的**后方**掠过 → 加速；从**前方**掠过 → 减速；越近效果越强，太近撞毁。

### 5.3 时间模型（D2）

- `Aiming`：物理时间冻结，行星固定在 `phase0`。
- 松手瞬间：
  1. 行星相位归零（`phase = 0`，即用 `phase0` 作为 t=0 姿态）；
  2. 探测器以玩家设定的发射向量出发；
  3. 物理时间开始推进，行星按周期公转。
- **预测轨迹与真实轨迹共用 `Gravity.ts`**：预测 = 从当前发射向量出发、用同一积分器推演出 N 步。因此"预测线看见的"就是"松手后发生的"（在固定步长下应完全一致）。

### 5.4 相机（D3）

**✅ 已落地实现（`game/CameraRig.ts`；纯计算部分有单测，`CameraRigTest` 20 断言）。** 实际行为以实现为准：

- 单一 `Camera3D`，`Aiming` 与 `Flying` 每帧都重算，且**始终只有一个连续视角**（不做"全局/跟随"硬切）。
- **注视点 = 所有关键点包围盒的中心**（关键点 = 探测器 + 全部行星；顺序无关），
  **不是**"探测器到目标的加权中点"。依据是"包围盒展开程度"而非"探测器到目标的距离"：
  后者在探测器飞过目标时会先增后减，导致相机反直觉地拉近。
- **距离 = 把所有关键点都投影进画面所需的最小距离**，夹在 `[CameraMinDistance, CameraMaxDistance]` 内。
  🚨 **S3.1 修正（会话 23）**：旧公式是 `距离 = minDistance + 半对角 × fitFactor(1.6)` ——
  一个**与相机无关的启发式**。竖屏（`aspect ≈ 0.56`）下横向可用空间只有纵向的一半，而透视还会
  **放大靠近相机的点**，于是位于包围盒角上的探测器**整个跑到画面外**（L3 截图实测：进关卡看不到
  自己的飞行器、预测线从画面外射进来 —— 子智能体只报了 stats，是**看截图**才发现的）。
  现在改为按**真实投影**求解：复用 `game/Projection.ts`（与渲染、预测线同一套已标定公式），
  在 `[min, max]` 上二分距离，直到所有关键点都落在"画面内缩 `margin = 0.05`"的安全区内；
  并把探测器的**模型外接半径**计入（`scene.probeRadius` = 局部 AABB 最大边一半 × scale × 1.1 ——
  它是**有体积**的，只约束质点会让碟形天线被画面边缘切掉；不取外接球，因为两根吊杆沿飞行轴伸出、屏幕不占宽度）。
  回归断言：`rig-frame-portrait-fits` / `rig-frame-probe-inside`（同一组关键点，旧算法 `ndcX = 1.11` = 出画）。
  `defaultRigOptions(fovYDeg, aspect)` 必须传 `View.fieldOfView` / `View.aspectRatio`；
  视口变化会重建关卡运行时，所以新宽高比自动生效（`init.ts` 的 `relayoutForViewport`）。
- **俯视倾角**固定 45°（安全区 20–60°，实测 >70° 贴边）：相机在注视点斜上方，
  高度 `sin(tilt) × distance`、进深 `cos(tilt) × distance`。
- **平滑**：注视点与距离各做一阶插值（`CameraLerp = 0.1`），**首帧直接吸附**（避免开场从原点飞过去）。
- **分辨率与视口自适应**：相机宽高比与所有 2D 几何都按 `View.size` 的**实际逻辑像素**推导，**不按设计分辨率缩放**；
  🚨 **视口变化（`onAppChange === 'Size'`）必须整体重建**，否则预测线错位、新区域收不到触摸。
  完整规则、实测数据与 `set-window.ps1` 用法见 §5.9。

#### 5.4.1 取景：局部集合 + 逐点半径 + 预算（S3.12）

用户原话：「玩家所面对的其实是**轨道的一部分**，不是能看到整个轨道。然后才能体现空间的宏大，
然后较远的地方可以看到一个发光的太阳。」—— 从前取景集合是"探测器 + **全部**行星"，
相机被迫一路拉远（甚至撑到 `CameraMaxDistance`），画面里什么都小、太阳还被画面边缘裁掉一块。

| 规则 | 内容 |
|---|---|
| **核心集合** | 探测器 + **下一站**；下一站的半径取 `max(本体半径, 到达容差)` —— 玩家真正要够的是那个"圈"，圈被切掉就没法瞄 |
| **锚点天体** | 场里 gm 最大且不绕别的天体转的那个：L2~L6 是太阳，**L1 是地球**（地月系没有太阳）。它让画面里有"远方那颗星" |
| **预算** | 锚点**装得下才装**：`CameraRig.wantDistance()`（纯查询、不动状态）算出的距离 ≤ `CameraFramingBudget`(240) 才加进去。否则宁可让它在画外 —— 它的光晕还会从边缘扫进来 |
| **逐点半径** | `CameraRig.step(points, probeRadius?, radii?)`：太阳半径 28，只约束中心点会让它压边（截图实测被裁掉一块） |
| **远处的行星** | **允许出画**。想看全景：捏合拉远（`observeZoom` 0.4–1.8）+ 开场分镜第 ② 段的全景 |

⚠️ 既有断言（`CameraRigTest` 的 20 条）在 `radii` 省略时必须逐位不变 —— `radii` 是**可选**参数，
缺省行为 = "只有 points[0] 用 probeRadius"。

#### 5.4.2 掠过自动慢动作（S3.17）：只改播放速度 + 相机贴近

设计稿定稿十条第 2 条：「掠过时**自动近景慢动作**（1/4 速、贴近行星），平时正常速度；给玩家 1×/2×/4× 兜底」。
触发口径（PLAN S3.17 已定稿，不再讨论）：「**最近接近任何天体**」—— 探测器与某个天体的距离进入阈值即进入
慢动作，**抵达月球与掠过木星共用同一套手感**，不用为「抵达」另写一套。

| 规则 | 内容 |
|---|---|
| **阈值** | `max(天体半径 × SlowMoRadiusFactor(5), SlowMoFloorDist(8))`（世界单位）：木星 23.2（盖住 17.6 的到达容差 ⇒ **抵达即慢动作**）、月球 8（地板，盖住容差 5）、地球 8.8（< L1 探测器轨道半径 10 ⇒ 起飞不误触发）。**锚点天体（太阳）排除**：它半径 28，任何 ≥3 的系数都会让阈值 ≥ 出发距离 80 ⇒ 六关全程慢动作，机制失效 |
| **只改播放速度** | 飞行在发射那刻就整条算完（`core.flight = simulate(...)`），回放只是取索引 ⇒ 慢动作 = 「每帧推进的模拟时间」变少。**唯一入口**是 `coreUpdate` 里的 `core.flightTime += dt * core.playback * (core.slowmo ? SlowMoFactor : 1)`：不重算物理、不动确定性、不引入第二套时钟（`tWorld = core.t0 + core.flightTime` 仍是唯一事实来源） |
| **系数基准** | `SlowMoFactor = 0.25` 是**相对手动档**的 1/4：默认手动 2× ⇒ 慢动作 **0.5× 实时**；玩家切 4× ⇒ 1× 实时；切 1× ⇒ 0.25× 实时。（写进注释：不是 0.25× 实时、也不是 1.5×） |
| **取景** | 慢动作期间关键点换成 `[探测器, 被掠天体]`（逐点半径；锚点/目标环出画，特写让位），`CameraRig.step` 第 4 个参数把距离下限放到 `SlowMoCloseDist(26)`（否则 `CameraMinDistance = 60` 把"贴近"吃掉：实测相机只从 ~110 收到 60、木星在画面里只大 1.8 倍）。仍是同一个求解器，**没有第二套取景** |
| **兜底** | HUD 左下角 1×/2×/4× 三颗**状态型**按钮（`fireOn: 'release'`，与时间流按钮共用 `createButton` 的 0.5 秒防抖；每次动作一行日志），仅 `Flying` 态可见（隐藏即断触摸）；高亮跟着 `GameCore.playback` 走，按钮不自己存状态 |
| **证据** | `slowmo-*` 9 条 + `playback-*` 6 条（`GameTest`）+ `rig-slowmo-*` 4 条（`CameraRigTest`）；引擎端 `slow-mo engage/release` 与每 0.5 真实秒的 `flight t=… speed=…` 日志行（同样帧数下 speed 2.00→0.50） |

### 5.5 轨迹渲染（最关键的视觉元素）

需求：一条发光的曲线，**实时**随拖动重画（预测线）；发射后同一个视图切成真实尾迹。

已确认的约束：

- `Line` 是 **2D** 折线（`Vec2[]`），不能直接放进 3D 世界画 3D 折线；`View3D` **没有** world→screen 投影 API。
- **2D 绘制节点（`DrawNode`/`Line`/`Label`）必须挂 `Director.ui` 或其 2D 子层**，不能挂 `Director.entry`（它是 `View3D`）。

**方案：2D 覆盖层 + 自建投影（`game/Projection.ts`，R4 已关闭）**

用“对已知世界点搜索射线方向点积最大的屏幕位置”作为真值，实测确定了：

| 项 | 实测结论 |
|---|---|
| `viewPoint` 坐标空间 | **像素坐标，原点在屏幕左下角**、**+Y 向上**：`x ∈ [0, W]`、`y ∈ [0, H]` |
| 相机手性 | `right = cross(forward, up)`（`HANDEDNESS = 1`） |
| 视野 | `View.fieldOfView` 是**垂直** FOV（度）；`focal = 1 / tan(fovY/2)` |
| 投影公式 | 见下方（`FLIP_Y = false`） |

```
f = normalize(target - eye)
r = normalize(cross(f, up))      // 手性：注意不是 cross(up, f)
u = cross(r, f)
vz = dot(p - eye, f)
ndcX = (dot(p-eye, r) / vz) * focal / aspect
ndcY = (dot(p-eye, u) / vz) * focal
viewPoint = (W/2 + ndcX * W/2,  H/2 + ndcY * H/2)   // 左下原点、+Y 向上
project(p) = (ndcX * W/2,       ndcY * H/2)          // 中心原点、+Y 向上（= Dora 2D 空间）
```

- 实现：`game/Projection.ts`（纯函数，无引擎依赖）；标定与回归：`Test/ProjectionProbe.ts` 反复 `RESULT=PASS`。
- **实测精度**：最大像素误差 **1.00 px**（2024×1230，约 0.05%）→ 关闭 R4。
- 🚨 **重要修正（S2 阶段实测发现）**：`getRayDirection` 的 viewPoint 是
  **左下角原点、+Y 向上**（不是早期误判的“左上角 +Y 向下”）。标定时的中心点检验对 Y 翻转不敏感，
  所以 1 px 的精度是真的、方向却是反的；后经**颜色标记球对照渲染位置**才定位
  （绿=探测器、红=火星、白=注视点标记球 —— 白球精确渲染在窗口中心，而另两球与 `project()` 输出
  恰好关于屏幕中心**上下镜像**）。⇒ **`project()` 的输出已是中心原点 +Y 向上，与 Dora UI 空间一致，
  `toOverlay()` 是恒等变换**。旧版多翻一次，导致所有 2D 覆盖层（预测线）垂直镜像于真实渲染 ——
  玩家看到的就是“预测线不从探测器出发”。
- **屏幕方向语义（修正后）**：世界 +z（靠近相机侧）渲染在屏幕**下方**，远离相机（-z）在**上方**（近景在画面下方）。
  游戏中探测器在屏幕下方、目标在上方，向上发射。

**发光效果**：高亮色 + `blendFunc` 叠加 + 略粗的 `drawSegment`；圆头靠“每段 `drawSegment` + 每个顶点补一个 `drawDot`”。
**预测线与真实尾迹必须用同一套采样数据**（同一个 `simulate` 的结果），避免“看起来一样、其实不一样”。

**✅ 已落地实现（`game/Trajectory.ts`，S1.3 已验证）与实测坑**：

1. ⚠️ **用 `DrawNode.drawSegment`，不要用 `Line`**：`Line` 的线宽**不可控**（约 1px），在 2024×1230 下几乎不可见。
   实测：改用 `DrawNode` 后，区域检测从 **11 个 → 40+ 个**，亮像素占比 **0.07% → 0.30%**。
2. **性能**：逐段绘制开销大，靠 `decimate(points, maxPoints)` 均匀抽稀（保留首尾）控制段数。
3. **投影预计算**：每帧要投影数百个点，用 `prepareCamera()` 算一次相机基，再用 `projectPrepared()` 逐个投影。
4. ⚠️ **`Vec2` 是 float32**（引擎 C++ 类型）：与 float64 普通对象比较会有 ~1e-8 相对误差；
   断言应把两边都降为 float32 再逐位比较，而不是用绝对容差。
5. 🚨 **预测线必须每帧重画**（不能只在拖动时重画）：重试后相机会用 lerp 从飞行终点视图滑回瞄准视图
   （约 20–30 帧）；若只在拖动时画一次，线会冻结在过渡中途的投影上，看起来“不是从探测器出发”。
6. 🚨 **S3.2 重画（会话 25，按用户反馈）**：预测线 = `drawSegment` 逐段**虚线**（12 实/9 空 px）+
   沿线渐隐（幂 1.35、末端残留 0.10——保留弹弓远端信息）+ 光晕垫底；尾迹 = **彗尾**（只留最近 280 采样点
   ≈1.2s，宽度/alpha 向尾部收窄 + 头部亮点），不再全程显示一条线。⚠️ 两个新坑：
   ① `BlendFunc(One,One)` 下 color 的 **alpha 不参与混合**（首版把衰减写进 alpha 完全无效）——
   亮度必须**预乘进 RGB**；② 圆头线帽会向虚线间隙延伸，`dashOff` 必须 > 2×(主半径+光晕半径)，
   否则间隙被桥接成实线。
7. 🚨 **投影输出的空间 ≠ 绘制层的空间**（S2.2 踩到的“整条线平移半个屏幕”）：
   `project()` 输出的是**相对屏幕中心的偏移**，而挂在 `levelLayers[i]` 下的 `DrawNode`，其局部坐标是
   **左下原点绝对像素 `[0,W]×[0,H]`**（父层 `size = View.size`、`anchor = (0.5,0.5)`、`position = (0,0)`）。
   S2.2 把 2D 层从“直接挂 `Director.ui`”改成挂容器后空间变了、代码没跟上 ⇒ 静止时整条线在画面外、
   拖动时出现在错误位置（用 `(0,0)` / `(W/2,H/2)` / `(W/2,H/2−530)` 三个标记点截图定位：
   红点落在左下角、绿点在正中心、黄点正好压在探测器模型上，而探测器的 `project()` 值是 `(0,-530)`）。
   ⇒ **偏移量必须显式传参**：`TrajectoryOptions.layerOriginX/layerOriginY`（`defaultOptions()` 取 `View.size` 的一半），
   **不要**在函数内部读全局 `View.size` 当隐式约定 —— 那样测试抓不住。
   回归断言：`TrajectoryTest` 的 `layer-origin-is-half-view`（该文件共 11 断言）。
8. 🚨 **预测线只在"玩家瞄过之后"才存在**（S3.12，用户原话：「预览线有时候调整好了又会变回初始状态，
   比如第一关，默认就不要显示预览线，调整过了再显示」）：
   - 进关时**一条线都不画**。旧版在 `!dragging && idlePath !== undefined` 时把**待机轨道**
     当预测线画出来（`setPrediction(idlePath.points.slice(idx))`）—— 它既不是玩家的意图，
     又会在玩家**松手（进 `Armed`）之后把他的线覆盖成初始状态**。
   - 现在由 `Game.ts` 的一个 `aimed` 标志守：`onAimDrag` 第一次触发时置真；`retry/startLevel` 置假。
     `!aimed` ⇒ `clearPrediction()`。
   - 缓存键（决定"要不要重算物理"）必须含 **日期 `tNow`** 与 **探测器此刻的位置 `probePos`**：
     行星位置随日期变、L1 的探测器自己在动，漏掉任何一项都会留下一条对不上物理的旧线。
   - "探测器自己在绕地球飞"这件事由**探测器本体的运动**表达，不要用预测线表达。
9. 🚨 **轨道器模式下的制动窗口预测（ADR D8，方案 A）**：
   - 基础线始终呈现未经主动制动的自然飞掠虚线；
   - 纯函数预积分中对目标天体引力影响区内的采样点做反向冲量试算，若满足束缚能量与安全近拱点条件（$E_{rel} < 0$ 且 $r_{peri} > R_{body} \cdot (1 + \text{安全缓冲})$），该段标记为 `Braking Window`；
   - 渲染为**琥珀金高亮光轨段**，给玩家明确的“飞入此段即可点击制动”的视觉规划引导。详见附录文档 §19.1。

### 5.6 关卡数据

**✅ 已落地实现（`game/LevelData.ts`，S2.1 已验证）**。实际字段以实现为准：

```ts
interface PlanetVisualDef { r; g; b; displayRadius; ring; model?: string; }  // model = 'Planet_Mars' 之类，留空回退 Sphere.gltf（S3.1）
interface GoalSpec {
  kind: 'planet' | 'escape';
  planetIndex: number;  // kind='planet' 时有效
  tolerance: number;    // 必须 > 目标行星半径，否则不可达
}
interface LevelDef {
  id; title; brief;          // title = 章节名（选关按钮上），brief = 关间一句任务简报
  probeStart: P2;
  planets: Body[];           // 复用 Gravity.Body（gm/radius/公转参数）
  visuals: PlanetVisualDef[];
  goal: GoalSpec;
  escapeRadius; maxSteps;
  homeRadius: number;        // 家园锚点（地球）的显示半径：逐关变小（S3.6.1）
  timeWindow?: { span };     // 有时间轴的关卡给「发射窗口」滑杆的量程（秒）；省略 = 没有
}
```

- `findGoalIndex(points, bodies, goal, dt, t0?)` — 在飞行采样点中找第一个进入容差的索引；
  **目标行星移动时逐点用 `t0 + i·dt` 时刻的位置判定**。
  ⚠️ `dt` 必须是**采样点之间的有效步长**：采样间隔 N 步时要传 `N · PhysicsStep`
  （传 `PhysicsStep` 会让移动目标的时间轴错位 N 倍 —— 2026-09-26 在扫掠里实测到并修掉）。
- `scaledPlanets(level)` — 应用全局倍率后返回行星数组（不改原始数据）。
- 结算在**发射瞬间**即可完全确定（轨迹 + goalIndex + outcome 都已知）—— 确定性设计的直接推论。
  到达目标后飞行在到达点截断收束（回放时间吸附到终点）。

> **载具模式与硬件区分**：
> - 内圈任务（L1 ~ L3）：太阳光照强，标配太阳能板版机体（`probeVariant: 'solar'`）；
> - 深空任务（L4 ~ L6）：因远离太阳光强衰减，标配 RTG 核电池版机体（`probeVariant: 'rtg'`），抛物面高增益天线始终动态逆向回指地球；
> - 轨道器型（L4）：赋予在轨制动发动机与 `[ BRAKE ]` 按钮，发射前预测线呈现高亮制动窗口，交会时联动慢镜头特写。

1. **这一版的能量主要来自太阳**：星际转移是“绕日弧线”，向内飞被加速、向外飞被减速。行星的引力只提供
   **改向** —— 开普勒时间压缩之后行星自己跑得慢，弹弓的能量收益 ≤ 7%（见 `LevelData.ts` 文件头）。
2. **圆轨道速度 `v = sqrt(SunGm / r)`**：r=80 处 = 30、逃逸 42.4。**静止出发的探测器想飞到 r 要多快
   是算得出来的**：远地点 105 需要 Δv ≈ 32、135 需要 33.6、195 需要 35.7（都在 45~55 的预算里）。
3. 行星轨道速度 = `2πR / T`（`T = KeplerK · R^1.5`，见 §5.3）。想让行星“挪得看得见”就调 `KeplerK`，
   不要单独改某颗行星的周期（那会破坏开普勒比例、也会让相位设计器算错）。
4. **L1 的月球周期是玩法参数**（120 秒，不是 276）：60 秒的时间轴跨度 = 月球走过 180°，“挑时机”才成立；
   飞行 2 秒里的漂移只有 6°，远小于容差。
5. **行星的引力越强，串联航点越“细”**：L6 曾给木星 gm 9400，四站串联成功率被压到 3.3% 且**与容差无关**
   （强引力把后续航点的落点搅散了）。⇒ 巨行星的 gm 统一在 1200~12000 这一档。
6. **相位必须用工具解，不能手填**（S3.11 的教训：L3/L5 的相位曾照一条**撞进太阳**的弧线排，任何日期都对
   不上，成功率被压到 0.2%~6%）：`node tools/level-phases.mjs <关> --t0 <目标日期>` 解相位 →
   `node tools/level-window.mjs <关> --shifts ...` 把日期带挪到想要的位置（**关键事实：把每颗行星的
   phase0 一起减 ω·δ 等价于把整条日期带平移 δ 秒**，所以不需要重解相位）→ `tools/level-sweep.mjs` 复扫。

**可玩性硬门（`Test/LevelDataTest.ts`）**：每关做**角度×力度扫掠**，必须至少存在一个可行解
（12×4，带时间轴的关卡再乘 24 个日期档；捞不到解才升到 24×6 或刹车模式），且时间轴的窗口必须真的有形状
（`lvN-window-matters`）。调数值时**别用引擎跑**：`node tools/level-sweep.mjs`（Node 里跑同一套公式，
秒级）先把数值收敛，再进引擎验收。

#### 5.6.2 时间轴（`SimOptions.t0`）

行星位置本来就是时间 `t` 的函数，所以"把发射时刻往后拨 t0"在物理层只需要**一个入口**：
`SimOptions.t0`（`simulate` 从它开始累加时间，省略 = 0，与旧行为逐位一致）。
**预测线与真实飞行必须传同一个 `t0`**，否则又是"看到的 ≠ 飞到的"（与 §4.1 的确定性要求同源）。

**"窗口"的判据（S3.11 修正，已写进单测）**：

- 曾经写过"t0=0 无解"，实测做不到 —— 单次点火有**方向 + 力度两个自由度**，一个自由度就能补偿整个
  日期的偏差（实测把木星错开 95° 仍能靠改方向蒙中 1 条）。第二轮改成"至少要有一个 t0 档零解"，
  它当时能过，但那是**假象**：那一版 L4 的相位照一条撞太阳的弧线排，大半时间轴是死区。
- 相位修对之后，判据改成**两条可观测的表述，满足任一即可**：
  ① 有的时机**完全没解**（窗口真的会关 —— L6 单程：前 4 档零解）；
  ② 起点明显差于最好时机，**至少 2 倍**（L4 窗口：t0=0 有 3 解、峰值 8 解）。
- **设计发射日期时要记住**：可行日期带本身有宽度 ≈ `方向窗口 ÷ 行星角速度`（L4 ≈ 180 秒）。
  答案放得不够远（比如 t0\*=90），t0=0 也会是可行解，这一关的教学（"挑时机"）就没了。

#### 5.6.3 行星相位**必须用工具解**（S3.11 的教训）

**症状**：L3/L5 的扫掠成功率只有 6% / 0.2%，玩家说"关卡诡异、不知所云"。

**根因**：`orbiter(gm, radius, orbitRadius, phaseDeg)` 的最后一个参数是"行星 t=0 时在哪个方位"。
旧值是照着一条"设计航线（240° 方向、Δv 35）"排的 —— 实测那条弧线 **peakR 只有 80**：
它朝太阳飞，直接撞进太阳（半径 28）。于是相位和任何真实航线都对不上，整关只剩极限运气解。

**做法**：`node tools/level-phases.mjs <关卡> [--t0 N] [--tol ...] [--nocapture]`

1. 只留**太阳**做仿真（行星引力置 0）⇒ 得到一族"绕日弧线"，每条记下它依次穿过每个航点环的
   (角度 θ, 时刻 t, 速度 v)。
2. 把航点 i 的行星摆成 `phase0_i = θ_A,i − ω_i·(t_A,i + t0*)`（= 让弧线 A 在第 t0* 秒正好撞上它），
   则另一条弧线 B 能在第 i 站被接受 ⟺ `r_i · angdiff(θ_B,i, phase0_i + ω_i·t_B,i) ≤ tol_i`
   （捕获站再叠一条相对速度阈值）。
3. 取"**能走通的弧线最多**"的那组相位 —— 这正是设计稿第五章要的"多条路线"。
4. 写进 `game/LevelData.ts` → `node tools/level-sweep.mjs` 复扫 → 引擎内 `Test/UnitRunner` 验收。

**实测收益**：

| 关卡 | 相位（旧 → 新） | 细网格成功率 |
|---|---|---|
| L3 弹弓 | 195.5 / 198 → **89.4 / 89.0** | 8.6% → **42.5%** |
| L5 大巡游 | 195.5~216.4 → **89.5 ×4（连珠）** | **0.2% → 17.5%** |
| L4 窗口 | 315.5 / 288 → **29.3 / 48.2**（第 180 秒对齐） | 1.1% → **8.9%** |
| L6 单程 | 200/245/290/335 → **29.3 / 48.2 / 58.9 / 65.7** | 32%（无决策）→ **2.7%**（四站 + 逃逸 + 时机） |

**为什么"连珠"的相位都在 89.5° 附近**：能依次穿过 105/135/165/195 四个环的那族弧线**接近径向**
（θ 沿径向不变），所以行星必须摆在那条射线上 —— 这也正是真实 Grand Tour 能成立的原因
（八十年代外侧四颗巨行星恰好连珠）。

⚠️ 工具里的是**解析近似**（忽略行星引力与遮挡），只用来产生相位；权威判定永远是
`tools/level-sweep.mjs`（真实物理）与引擎内的 `Test/UnitRunner`。

### 5.7 输入与交互

- 单指拖拽。实现用节点触摸回调：设置 `node.touchEnabled = true` 后使用 `onTapBegan / onTapMoved / onTapEnded`
  （`touch.location` 是**接收节点局部坐标**；`touch.viewLocation` 是视图逻辑坐标）。
- 拖拽语义（在 `Aiming`）—— **2026-09-24 按用户真机反馈改为相对拖动（虚拟摇杆）**：
  - **按下点 = 摇杆零点**：按下瞬间瞄准归零到“直飞”（正对目标、最小力度），预测线立刻显示中性方向；
  - 之后的**位移**（相对按下点）决定方向与力度：位移方向 = 发射方向（屏幕上 = 直飞，右 = 右偏），
    位移长度 = 力度（夹紧到 min/max）⇒ **按在哪里都能瞄**；
  - 拖动过程中**每帧重算并重画**预测轨迹；
  - 抬起 = 松手 = 发射（不可撤销，愿景 §3/§15）。
  - 旧模型（“探测器位置 → 触摸点”的绝对方向，按下即按距离给力度）已废弃：真机上按下位置与探测器位置
    无关联，玩家一按就拿到了力度、方向也由按下点决定，与手感预期不符（用户反馈“按下的地方也不是飞行器所在的地方”）。
  - 实现上复用 `computeAim`：把按下点当作它的 `probeOffset`；程序化缝隙 `handleOffset`/`handleLocal` 的参数语义
    同步改为“相对按下点的位移”。
- UI 按钮（结算、关卡选择）必须是**可见可点**的 2D 按钮（触屏目标足够大，竖屏下拇指可达）。
- 全流程必须触屏可完成（开始 → 游玩 → 结算 → 重开）。

**✅ 已落地实现（`game/Hud.ts`）与关键实现要点**：

1. **统一坐标空间为“投影偏移空间”**（中心原点、**+Y 向上**，即 `project()` 的输出空间）。
   探测器屏幕位置直接来自 `project()`，触摸位置经 `localToOffset()` 换算：
   `offset.x = local.x - W/2`，`offset.y = local.y - H/2`
   （全屏节点局部坐标是**左下原点、+Y 向上**，两个空间同向，只差中心平移）。
   ⚠️ 修正后：平面 y 轴与偏移 y 轴**反向**（平面 -y = 朝目标 = 屏幕上方），所以瞄准方向必须取 `uy = -dy / len`
   （S2 修投影镜像时曾误删此负号，被 `HudTest` 当场抓回）。
   ⚠️ 初版把“`project()` 输出”与“触摸换算”当成同一空间直接相减 —— 当时两者反向，方向会算错。
2. 🚨 **全屏触摸容器的 `anchor` 必须是 `(0,0)`**（会话 18 修正，真机踩过）：节点的**子坐标原点 = 位置 − anchor × 尺寸**，
   取 `(0.5,0.5)` 会把整棵子树（含**触摸命中框**与 2D 绘制原点）再推走半个屏幕 ⇒ **命中框只剩左下象限**：
   view x ≳ W/2 或 y ≳ H/2 处按下**完全没有事件**。实测六点网格（每点重新进关）：`(200,200)`、`(1800,200)`、
   `(200,1000)`、`(1800,1000)`、`(1012,615)`、`(600,400)` 全部 `began view=… local=…`（两者一致）。
   现结构：根节点 `size = View.size`、`anchor = (0,0)`、`position = (0,0)`；内部再挂一个 `size = View.size`、
   `anchor = (0.5,0.5)`、`position = (W/2,H/2)` 的 `touchLayer` 接收触摸 —— 命中框正好等于整屏，
   且 `touch.location` 与 `localToOffset()` 的假设一致。
3. **`Touch` 是私有构造，无法程序化注入** ⇒ 真触摸坐标系历史上只能人工校对（`localToOffset()` 是唯一校准点）。
   ✅ **现在的替代路径（Windows 桌面）**：Dora 的触摸事件**同时代表鼠标点击**，用 `tools/input-inject/mousectl.ps1`
   合成鼠标事件即可驱动真实命中判定与状态机（见 §8.1 与 §9）。⚠️ 真机多点触控/手势差异仍建议人工抽查。
   `handleLocal` / `handleOffset` 是为键盘降级 / 回放 / 无头测试保留的输入缝隙。
4. **接口用属性式箭头函数类型**，且返回对象里不要用简写属性引用局部函数（会触发 TS100016 “无 this 转换”错误，
   包一层箭头函数即可）—— 与 §7.2.1 同源。
5. 调参：`AimMinSpeed=2` / `AimMaxSpeed=22` / `AimMaxDragPx=380`（`Config.ts`）。
6. **2D 原语集中在 `game/Ui.ts`**：`createPanel`（实心矩形，`DrawNode.drawPolygon` 四顶点）/ `createLabel`（居中锚点文字）/
   `createButton`（**自身即可点节点**：底色 + 居中 Label + `touchEnabled`/`swallowTouches`/`onTapEnded`，按下换底色）。
   字体名、配色、触屏下限都只在这个文件里改。颜色用 `0xRRGGBB` + 单独 alpha；取通道用除法而不用 `>>`/`&`
   （位运算在 TSTL 各 Lua 目标上支持面更窄）。
7. **锚点统一 `(0,0)`、局部绘制 `[0,w]×[0,h]`**：d.ts **没有**写明 `anchor`/`size` 与“子节点坐标系 / 触摸命中矩形”的关系。
   `anchor = 0` 时两种解释重合 ⇒ 画出来的矩形与命中矩形必然一致；代价是按**左下角**摆放。
8. 🚨 **每个全屏触摸层都要随“是否在玩这一关”开关 `touchEnabled`**（S2.3 实测）：`swallowTouches = true` 的层会**独占**
   它收到的触摸。多关并存时，上一关的瞄准层若还开着，屏幕上的点击全被它吞掉，第二关表现为“怎么拖都没反应”。
   `AimInput.setEnabled` 现在同时改内部开关与 `touchLayer.touchEnabled`。
   ⚠️ `onTap*` 注册时会把 `touchEnabled` 置回 true，所以“初始关闭”必须写在**注册之后**。
9. **按钮不做坐标过滤**：Dora 没有“触摸取消”回调 —— 按下后划出按钮再松开，`onTapEnded` 仍会触发。
   这里选择“多触发一次”，而不是用 `touch.location` 判定是否松开在按钮内（空间假设错了会让按钮**整块点不到**）。
10. **触屏目标尺寸：按可用空间算，绝对下限只保“地板”**（2026-09-24 竖屏实测修正）：
    - 竖屏窄屏（`View.size = 601×1066`，来自 400×710 客户区）时，旧写法“高 ≥ 130 / 宽 ≥ 560”**直接溢出**：
      6 行 ×130 + 5×18 间距 = 870 > 可用 636 ⇒ **L6 被裁一半、底部提示整条被挤出屏外**；
      结算卡片宽只有 529，而按钮写死 ≥560 ⇒ **按钮横向戳出卡片外**（两处都有截图证据）。
    - 现规则：列数随宽高比**自适应**（竖屏 **2 列×3 行**、横屏 1 列×6 行）；按钮尺寸由可用空间推算（`availW`/`availH`）；
      绝对下限降到 `MinButtonWidth=160` / `MinButtonHeight=72`（只防“小到点不中”）；结算按钮宽 = 卡片宽 − 60，
      卡片若高于屏幕则先压按钮高度。
    - 全部按 `View.size` **实际逻辑像素**推导，不按设计分辨率换算 ⇒ **设计分辨率（1080×1920）不再是约束**（见 §12）。
11. 🚨 **视口变化必须重建整层**（会话 20）：触摸层与面板的几何都按 `viewW/viewH` 算死，`View.size` 一变就必须重建
    （含 `size = View.size` 的触摸层与它内部的 `touchLayer`），否则新区域收不到触摸。详见 §5.9。
12. **`Label()` 可能返回 undefined**（字体缺失）：`Ui.ts` 的 `setLabelText/setLabelColor/setLabelCenter` 一律容忍 undefined，
    调用点不必到处写 `if`。
13. **`View.size` = 窗口客户区像素 × 1.5**（引擎渲染尺寸；实测 400×710 客户区 → 601×1066）。
    代码只读 `View.size`，不要读窗口/客户区尺寸，也不要对这个系数做任何假设（不同平台/缩放会变）。

#### 5.7.1 瞄准与观察的分区（**已实现**，会话 41 / PLAN S3.10）

**落地形态**（与下面的设计一致）：`AimInput` 只保留**一个**全屏触摸层，`onTapBegan` 里算按下点到探测器的距离，
≤ `max(96, viewW × 0.25)` 记 `mode = 'aim'`，否则 `mode = 'observe'`；松手时 aim 走 `onAimReady`（进 `Armed`，**不发射**），
observe 走 `onObserve`（像素增量 → 相机）。缩放用引擎自带的 `onGesture(center, numFingers, deltaDist, deltaAngle)`。

用户 2026-09-26 定稿：发射前允许**自由观察**，因此把"拖一下就是瞄准"改成**按落点分区**：

- **探测器附近**（≤ `R_aim` ≈150 view px）拖动 = **瞄准**：出预测线 + Δv 读数，**松手不发射**，
  而是进入 `Armed` 态并显示「发射」按钮；
- **其他地方**拖动 = **自由观察**（绕焦点转、捏合调距离、点天体切焦点）；
- ⚠️ **只用一个全屏触摸层**，在 `onTapBegan` 里按落点判模式。开两层（一层瞄准一层观察）必然互相吞点击
  （硬约束 4）。命中判定也要照顾"手指落点 vs 探测器在屏幕上的位置"——探测器位置由主循环每帧投影得到。

**「发射」按钮的纪律**：只在 `Armed` 态 `setEnabled(true)`，其它时候隐藏 + **断触摸**；
并且 `Armed` 必须是 `GameCore` 里一个**真正的状态**（与 `Aiming/Flying/Result` 并列），
这样"面板/按钮显隐由状态驱动"这条规则才成立（见 §5.9.1）。

#### 5.7.2 按钮回调的两个坑（2026-09-26 实测）

1. **不要自己往 `createButton` 返回的 `root` 上挂 `onTapBegan/onTapEnded`**：它内部已经注册过，
   后注册会把它的处理器**顶掉** —— 表现为"按下去既没有按下反馈、也拿不到回调"。要按钮行为就用它自己的 `onTap`。
2. **回调签名必须收 `touch` 参数**：d.ts 是 `onTapBegan(callback: (this: void, touch: Touch) => void)`，
   写零参数的箭头函数会**编译失败**（`This expression is not callable`，报错信息完全指不到问题）。

#### 5.7.2b 需要"按住"的按钮：用 `createButton` 的 `onPressBegan/onPressEnded`（S3.11）

时间流按钮（「◀ 回退 / 加速 ▶」）从"点一下走 15 秒"改成了**按住即走**：
按下即走一步（= 原来的点按语义）→ 停 `WarpHoldDelaySec`(0.3 s) → 按 `TimeWarpRate`(40 倍) 连按，松手即停。
（L4/L6 的时间轴有 300 秒，只靠点按要按 20 次。）

- `ButtonOptions` 增加 `onPressBegan? / onPressEnded?`，**在 `createButton` 内部**从 `onTapBegan/onTapEnded`
  里调用 —— 外部仍然不碰节点的触摸回调（硬约束 6）。
- ⚠️ 这两个钩子**不走 0.5 秒防抖**（那条防抖是给 `onTap` 的"同一瞬间双投递"用的），
  所以**实现必须幂等**：`onPressBegan` 里"已经在按住同一个方向就直接 return"，
  `onPressEnded` 里"方向对得上才清零"。
- 连按需要一个每帧的驱动：`AimInput.update(dt)` 由主循环（`init.ts`）每帧调用。
- **相态守卫**：`coreTimeWarpAllowed(core)`（只有 `Aiming` / `Armed` 能改日期）。
  飞行用的是 `tWorld = t0 + flightTime`，飞行途中改 `t0` 会让行星在**飞行路径底下跳位**。
  HUD 侧读同一个判据（`AimInput.setTimeEnabled`）——**按钮可点性与游戏逻辑必须是同一个事实来源**。

#### 5.7.2c 一次性按钮必须"按下即动作"（S3.12）

`ButtonOptions.fireOn`：`'release'`（默认，历史行为）/ `'press'`（按下即触发）。

**为什么**：Dora 的 `onTap` 挂在 **`onTapEnded`（松手）**上，而引擎**会丢事件**、
也**没有"触摸取消"回调** —— 手指按下后划出按钮再松开，松手那一下可能落到别的节点上，
表现就是"按了没反应"（用户会话 44：「有的时候还是会出现按钮点击了没有反应的情况，比如发射按钮」）。
一次性动作挂在**按下**那一刻，就与"松手落在哪"无关了。

- 用 `'press'` 的：「发射」、「重试本关 / 返回关卡选择」、选关按钮、「重看开场」；
- 保持 `'release'` 的：时间流（◀/▶）与「惯性/刹车」—— 它们是**状态型**按钮，而且按住逻辑走 `onPressBegan`；
- 两者共用同一条 0.5 秒防抖（挡"同一物理按压被鼠标 + 触摸投递两次"），**幂等由调用方保证**
  （发射后相态立刻离开 `Armed`；重试后面板立刻收起）；
- 证据打点：`launch button fire (press)` —— 有这行 = 事件到了、逻辑也进了。

**证据**（`tools/level-play.ps1`，合成鼠标）：按住「加速 ▶」2.5 秒 ⇒ `stepTime dir=1` 连续 12 次
（clock 15→180，间隔 ≈0.39 s = 15/40）；飞行中按住 ⇒ **没有** `warp press`、只有
`time warp visible=1 enabled=0`（按钮已断触摸）；松手 ⇒ `warp release dir=1 hold=1`。

⚠️ **"隐形的 UI"排查**：`applyWarpState()` 里那条"状态没变就早退"的捷径要求**初值等于节点的真实状态**。
把`warpVisible/warpOn` 初值写成 `false`（"我想让它隐藏"）时，第一次 apply 会命中早退 ⇒
**没有时间轴的关卡（L1~L3/L5）会永远留着一个「发射日期」文字和一排能点的「◀ 回退 / 加速 ▶」**（截图实测）。
教训：**"状态 == 节点实际状态"要如实初始化**，别用"期望值"当初值。

#### 5.7.3 输入事件的"丢失"要先于逻辑排查

合成鼠标点击在这台引擎上**经常整个丢掉**（实测 6 次里只有 1 次进入游戏，日志里连 `tap:` 都没有）。
因此"点了没反应"的排查顺序是：

1. **日志里有没有那行 `tap: ...`**？没有 ⇒ **事件没送到**（不是逻辑问题）；
2. 有行但 `phase` 不对 ⇒ 状态不同步（看 §5.9.1）；
3. 有行、`phase` 也对，界面却没变 ⇒ 渲染/重建问题（优先查视口重建那条路）。

### 5.8 结算判定

| 结果（内部值） | 面板大字 | 条件 |

| `success` 借力成功 | `借力成功` | 探测器进入目标行星的“到达容差”内且未撞毁（或达成 `escape` 目标） |

- 结果面板给出“重试本关 / 返回关卡选择”（D5）。

#### 5.9.1 HUD 显隐必须由状态驱动（2026-09-26 一次"点了没反应"的根因）

**规则**：任何全屏面板 / 按钮的显隐，都以**状态机**（`GamePhase` / `ResultKind` / `Armed`）为准，
**不许**只由点击回调驱动。

- 踩过的样子：玩家点「重试本关」⇒ 面板收起 ✓；但如果状态被**别的东西**改了（切关、视口重建、
  回归脚本的自动序列），屏幕上会留下一个"还在、但已经没东西可改"的面板 —— 点它完全没反应，
  看起来像按钮坏了；
- 现在的做法：`init.ts` 的 `onPhase` 里，**一旦离开 `Result` 态就收起结算面板**；
  面板还认**它自己显示的那一关**（`resultIndex`），而不是 `activeRuntime()`；
- 每次点按都打一行带状态的日志（`tap: retry (resultIndex=0 phase=Result)`）—— 这一行是"事件到了没有"
  与"状态对不对"的分水岭（配合 §5.7.3）。

#### 5.9.1b 太阳（恒星）怎么"发光"（S3.12）

用户原话：「太阳本身不发光就算了，还有点过于小了。」三件事，各有各的坑：

1. **它自己得是亮的**：`Material3D.emissive` **只有在配了自发光贴图时才看得出来**
   （星空背板用的就是 `setEmissiveTexture` + `emissive` 这一套）。只写 `emissive` 的话，
   太阳表面照不到自己（光在球心/背后）⇒ 渲染出来是一颗**灰球**（截图实测）。
   ⇒ `Assets/Image/sun_tex.png`（`Test/gen_glow.py` 生成，暖白、中心到边缘略降）。
2. **光晕**：`Assets/Image/glow.png` 贴在 `StarQuad.gltf` 上，材质 `baseColor` 留黑 + `alphaMode = Blend`
   （不 Blend 就是一块黑方块盖住星空）；`scale = SunGlowScale × 恒星直径`（`StarQuad` 是单位四边形，
   scale 就是直径）；每帧**绕 Y 转到正对相机**（只转一个轴 ⇒ 不受 Euler 次序影响），
   俯视造成的 Y 压缩用 `1/cos(tilt)` 在 scale 上补回。
3. **点光源试过，否了**：几何上唯一正确的位置是太阳中心，但同一盏灯没法同时照亮金星（55）与海王星（195）
   —— 强度 2.4 / 8.0 两档实测**外圈行星全部发黑**。⇒ 保留方向光（它的方位角是按截图标定的），
   "发光"由上面两条表达。

**读数可读性**：光晕会扫过左上角，纯文字在亮底上读不出来 ⇒ `Δv` 与 `发射日期` 底下垫一块
半透明暗板（`createPanel(..., { alpha: 0.45 })`，UI 在 3D 之上，所以是提高对比度而不是遮挡）。

#### 5.9.2 世界时刻 = 发射日期 + 已飞行时间（**只有这一个事实来源**）

时间轴（`core.t0`）一旦存在，**任何**按时间取行星位置 / 画环 / 判定的地方都要用 `tWorld = core.t0 + core.flightTime`。
踩过的现象（两次，同源）：瞄准段用对了、**飞行段漏了 `t0`** ⇒ 物理位置正确、**行星模型却跳回 t=0**。

##### 发射日期必须"交棒"（S3.12，第二次踩到同一个坑）

`GameCore.t0` 从 `createCore` 起就是 0，**全程只被读、从来没有被写过**；玩家用「加速 / 回退」拨出的日期
只活在 `clock`（瞄准期的世界时钟）里。于是：

| 阶段 | 用的时间 | 对不对 |
|---|---|---|
| 瞄准 / 预测线 / 行星位置 | `tNow = core.t0 + clock` | ✅ 是玩家选的日期 |
| `coreLaunch`（`simulate(..., t0: core.t0)`） | `core.t0` = **0** | ❌ |
| 飞行 / 结算 / 环 | `tWorld = core.t0 + flightTime` | ❌ 从 0 开始 |

⇒ L4/L6 里"调好了时间、一按发射行星就跳回原位"（用户会话 44 原话）。

**规则**：日期在 `clock`（瞄准期）与 `core.t0`（物理期）之间**显式交棒**，用纯函数 `coreHandoffDate(t0, clock, toT0)`：

- **发射**（`launch` / `launchArmed`，必须在 `coreLaunch` **之前**）：`clock → t0`；
- **重试**（`retry`）：`t0 → clock` —— **保留玩家挑好的日期**，L4 才能就着这个时机继续调；
- **进关 / 重新进关**（`prepareIdle`）：两者都归零。

⚠️ 两个方向的 `t0 + clock` **都守恒** —— 这就是"交棒瞬间画面不跳"的数学表述
（`dateNow()` 与瞄准期的 `tNow` 都等于 `t0 + clock`）。单测 `handoff-*`（4 条）守着；
引擎侧用 `tools/level-play.ps1 ... -ShotBeforeTaps` 抓"发射前 / 发射后"两张图，
比较**行星亮斑质心**的位移（实测 L4：木星 (-3.5, 0.5) px —— 那是它在继续走，不是跳位）。

#### 5.10 2D 规划视图（S3.15）

> 设计依据 [关卡舞台表.md](./关卡舞台表.md) 第二节第 3/4/6 条：**2D 线稿示意图 = 规划，3D = 观赏与回报**。
> 实现：`game/PlanView.ts`（纯映射 + 四层 DrawNode）与 `game/Game.ts` 的 `viewMode`。

**分层与切换**

- `GameCore.viewMode` 是视图的**唯一事实来源**（`'2D' | '3D'`）：
  - `coreLaunch` → 3D、`coreRetry` → 2D（相态流转的副产品；玩家手动切过，也会被下一次流转拉回该相态该有的样子）
  - `coreToggleView(core)` **只改 core 状态并返回新模式** —— 右下角那颗按钮只是它的另一个入口，**按钮自己不持有视图状态**
    （会话 38 那次「点了重试没反应」的根因同源：UI 显隐必须状态驱动，不能只由点按驱动）
- 进关 `Aiming` = 2D；发射后飞行与结算 = 3D；重试回 2D。
- 每帧由 `init.ts` 把 `core.viewMode()` 同步给瞄准层；`Game.ts` 里 `plan.setVisible(is2D)` 与
  `aim.setFullScreenAim(is2D)` 都由同一个 `is2D` 推导 ⇒ **不存在第二个真相**。

**平面 → 屏幕的映射**（`game/PlanView.ts`，纯函数、可单测）

- `computePlanMapping(viewW, viewH, radius, marginFrac)`：等比缩放，要能放下「最外圈轨道 + 目标容差」（留 ~12% 边距）
- `planeToScreen` / `screenToPlane`（逆，诊断与将来「点图定位」用）
- ⚠️ **平面 +y 映射到屏幕下方** —— 与 3D 的约定一致（俯视 45° 下「屏幕向上」= 平面 -y）。两个映射一致 ⇒ 2D 与 3D 的拖拽手感
  **结构上**相同，不靠调参。图钉与文字用**固定像素尺寸**（不随缩放）。

**两条硬约束**

1. **预测线与 3D 共用同一批点**：`Game.ts` 里 `plan.setPrediction(predPoints)` 收的就是 3D 轨迹视图那个数组 ——
   一个 `simulate`、两个投影。「看得见的那条线就是会飞的那条路」在 2D 里同样成立。
2. **不要第二套时间源**：`plan.syncBodies(bodies, visuals, tWorld)`，发射日期交棒（`core.t0`）自动生效；
   视口重建时必须 `plan.clear()`（DrawNode 挂在关卡 2D 层上，**不随 runtime 消失**）。

**2D 里的瞄准**：整屏拖动都算瞄准（`setFullScreenAim(true)`）——「探测器附近才算、别处拖动 = 自由观察」那条分区规则
是为 3D 服务的；2D 下 3D 世界整个收起来了，留着分区只会让大半屏变成死区。方向与力度的换算**复用 3D 那一套**
（screen → world → plane，`PlaneToWorldX/Z`），没有第二套数学。

**踩过的坑**

- ⚠️ 桌面开发版引擎**窗口底部有一条调试工具条**（退出 / 刷新 / ✓），落在那一带的鼠标事件会被**整个吃掉**
  （实测：按钮放 y=20 时点下去连 `view toggle fire` 都不打）⇒ 2D/3D 按钮摆在「发射」**正上方**（同一列、右边缘对齐），
  仍在右下角拇指区且完全避开工具条。
- 2D 层隐藏时必须同时断触摸（AGENTS 硬约束 4）：`setVisible(false)` 会清屏，触摸由 `setFullScreenAim` 统一管。

**验收**：构建 / 单测 / 截图（2D 线稿真的画出来）/ `level-play` 日志（按下发射切 3D）/ 手动切换 —— 全部由父 Agent 独立复核，见 PROGRESS。
#### 5.11 沿轨道流动的光点（S3.16）

> 用户原话：「轨道圈看不出运动方向与快慢」。实现：`game/OrbitFlow.ts`（纯数学、零引擎依赖）+ 两侧接线。

**三条设计硬要求**（单测 `Test/OrbitFlowTest.ts` 25 条守着）

1. **方向 = `Body.orbitDirection`**（读字段，不写死顺行 —— 将来加逆行天体，光点自动反流）；
2. **快慢 ∝ 角速度** `ω = 2π / orbitPeriod`（开普勒：内圈快、外圈慢，一眼看出谁跑得快）；
3. **位置只由 `tWorld` 解析求出** —— `orbitAngleAt` 与 `Gravity.bodyPositionAt` **同一个式子**，
   所以拨发射日期时行星与光点一起动，且不存在第二时间源。

**关键设计：光点链锚在行星此刻的角上**（第 k 个 = 行星角 + k·2π/N）。于是整条链以 ω 公转是**天然结果**，
不需要第二套动画时钟；且「第 0 个光点压在行星身上」成为**可单测的不变量**（光点几何与物理几何不可能分家）。

**两侧共用**：3D（`Scene.syncBodies(t)` 里每帧只写 position）与 2D（`PlanView` 的 DrawNode）共用同一个纯函数
与同一个 `FlowDotsPerOrbit = 6` ⇒ 两条视图里同一条轨道长得一样。3D 侧节点池**建场景时一次建好**（≤36 个 StarQuad，
复用太阳光晕的贴图与「baseColor 留黑 + emissive 贴图」配方），**不要每帧重建节点**。

**取证陷阱（重要）**：**L3/L5 在瞄准态 `tWorld` 是冻结的**（S3.9.4 只有 L1 有待机轨道 `idlePath`）⇒
那两关截两张图只能证明「光点存在」，**证明「在动」必须用 L1**（实测：月球链 16 秒 +47.7°、地球链 +8.0°、内圈快 5.96 倍）。

**未完成**：3D 受控 A/B 探针（固定相机 + 两个 tWorld 的对比）—— `GameScene` 是 `@noSelf`，在 Lua 里必须用**点号**调用，
写成冒号会让第一个参数串位（实测 `eye` 变成 scene 表、`Vec3.new` 收到 nil）。
#### 资产接线：S3.14 建模交付（贴图 / 环 / 两版探测器）

> 交付文档：[交付清单_Trae.md](./交付清单_Trae.md)（建模方自检） + [模型交接_Trae.md](./模型交接_Trae.md)（我们的规格）。
> 自检工具：`node tools/glb-check.mjs Assets/Model/Planet_Earth.glb`（直接读 GLB 二进制，不用起引擎）。

**交付事实（已核对）**：天体全部是**单位球**（POSITION min/max = ±1.00 ⇒ `k = 1.000`）；每个 primitive 都有
`TEXCOORD_0`；`images = 0`（**不内嵌贴图**，贴图在 `Assets/Image/` 里由代码绑定）；土星环在 xz 平面（±2.2）、
天王星环在 xy 平面（±1.95），两者的环材质都是 `doubleSided + alphaMode = BLEND`。

**贴图绑定的三条规则**（都收在 `game/Scene.ts` 的 `PLANET_TEX` + `applyPlanetTexture`，关卡与开场共用）：

1. **行星**：baseColorTexture = `planet_*.jpg`，同时把 `baseColor` 置**白** —— 贴图自己带颜色，
   不置白就会和关卡的视觉色相乘变成脏色（视觉色退化成「没有贴图时的回退球」的颜色）。
2. **自发光**：太阳用 `sun.jpg` 同时当 baseColor 与 emissive（乘数满值）—— `Material3D.emissive` 只有配了
   自发光贴图才看得出来，而太阳表面照不到自己（光的来向都在它内部或背后）；地球用

## 7. 编码规范

### 7.1 Dora/TS 硬规则

- **禁止** `any`。用具体类型、`unknown` + 收窄、泛型或精确联合。
- **禁止**裸 `null`。用 `undefined` / 省略字段（Lua 语义）。
- **工厂命名空间是值不是类型**：实例标注用 `Vec2.Type`、`Color.Type`、`Camera3D.Type` 等，不要写 `ReturnType<typeof X>`。
- **不支持** `Math.hypot`、`Math.imul`。用 `Math.sqrt(x*x + y*y)` 与普通算术。
- **可选返回值必须收窄**：如 `Model3D(...)` 返回 `Model3D | undefined`，`Label(...)` 可能返回 `undefined`。先用 `if (!x) throw ...` 或分支处理，再使用。
- **Lua 数组不能表示 `undefined` 元素**：不要用可选工厂结果直接拼数组。
- 缩进用**普通空格**，绝不出现字面 `\t` 两个字符。

### 7.2 TSTL（TS→Lua）坑（来自 `caveats.md`）

| 项 | 差异 | 规避 |
|---|---|---|
| 布尔真值 | `0`、`""`、`NaN` 在 Lua 中为**真** | 只用显式布尔表达式 |
| `==` / `===` | TSTL 中等价 | 无需纠结，但保持严格写法 |
| `null` / `undefined` | 都变 `nil` | 避免 `null` |
| 表键存在性 | 赋 `nil` 即删键 | 用哨兵值 `-1` 或自定义 `Null = {}` |
| 数组长度 | `.length` → `#`，中间空洞会出错 | 不要写中间为 `undefined` 的数组 |
| 迭代顺序 | 无序 | 需要顺序就用数组 |
| 局部变量上限 | Lua 局部变量 200 个 | 大函数拆小；必要时合并导出表 |
| **对象成员函数的 self** | 启用了 `noImplicitSelf`，但**对象/接口的成员函数依然默认带 self**，生成 `obj:method(arg)` 冒号调用 | 给 interface 加 `/** @noSelf **/`，或每个方法写 `this: void` |
| **工厂命名空间不能当类型** | `Vec3` / `Node3D` / `Color` 等是**值**，不是类型 | 标注用 `Vec3.Type` / `Node3D.Type` / `Color.Type` |

#### 7.2.1 已实际踩到的坑（写代码时必须避开）

**坑 1：对象成员函数默认带 self（会造成参数错位）**

```ts
// ❌ 错误：TSTL 生成 `scene:syncProbe(pos)`，
//    scene 会变成第一个参数，函数体内的 p 收到的是 scene → 报 “field 'x' is nil”
interface GameScene {
	syncProbe(p: P2): void;
}

// ✅ 正确：加 @noSelf，生成点调用 `scene.syncProbe(pos)`
/** @noSelf **/
interface GameScene {
	syncProbe(p: P2): void;
}

// ✅ 也可逐个方法声明
interface GameScene {
	syncProbe(this: void, p: P2): void;
}
```

⚠️ 注意：**用属性式函数类型（`syncProbe: (p: P2) => void`）不能解决这个问题**，仍会被当作成员函数。
这个错误编译期**不报错**，只在运行时莫名奇妙地报 “nil 值算术”—— 极难定位。

**坑 2：`threadLoop` 的返回值语义易搞反**

```ts
// threadLoop 回调：返回 false 继续，返回 true 停止
// ❌ return frame < 600;   → frame=1 时返回 true，循环立即停止（看起来像“卡住”）
// ✅ return frame >= 600;  → 正确
```

**坑 3：`App.saveScreenshot` 是异步落盘**

请求后**不能立即读**，会拿到**上一次的陈旧截图**（图像与上一次逐字节相同，极具迷惑性）。
正确做法：请求 → 隔几帧 → 读取。详见 §9.1。

**坑 4：不要用 `toExponential`**

TSTL 不支持 `Number.prototype.toExponential`。用 `toFixed` 代替。

**坑 5：子坐标原点 = 位置 − anchor × 尺寸（全屏容器的 `anchor` 必须是 `(0,0)`）**

```ts
// ❌ 错误：直觉上“居中”，实际把整棵子树（含触摸命中框）推走半个屏幕
const root = Node();
root.size = Size(viewW, viewH);
root.anchor = Vec2(0.5, 0.5);   // 子坐标原点 = 位置 − anchor×尺寸 = (−W/2, −H/2)

// ✅ 正确：挂在 2D 容器下的全屏节点用 (0,0)，子空间 = 父层的“左下原点绝对像素”
root.anchor = Vec2(0, 0);
root.position = Vec2(0, 0);
```

**现象**：2D 绘制原点整体偏移；**触摸命中框只剩左下象限** —— view 坐标 `x ≳ W/2` 或 `y ≳ H/2` 处按下**完全没有事件**。
本项目为此踩了**两次**：一次是预测线整体平移半个屏幕（§5.5 第 6 条），一次是真机“不是按哪里都能瞄”（§5.7 第 2 条）。
**正确做法**：全屏容器用 `anchor = (0,0)`；若确实需要 `(0.5,0.5)`（只想让节点自身居中），必须显式把 `position` 设为
`(W/2, H/2)` 或按半个尺寸补偿子节点坐标。d.ts 没有写明 `anchor`/`size` 与“子坐标系 / 命中矩形”的关系，**以实测为准**。

**坑 6：投影输出的空间 ≠ 绘制层的空间（层原点必须显式传参）**

- **现象**：`project()` 输出的是**相对屏幕中心的偏移**，而挂在 `levelLayers[i]` 下的 `DrawNode` 局部坐标是
  **左下原点绝对像素 `[0,W]×[0,H]`**；把前者直接当后者用 ⇒ 整条预测线被平移 `(+W/2, +H/2)`（静止时线在画面外，拖动时出现在错误位置）。
- **正确做法**：偏移量由调用方**显式传参**（`TrajectoryOptions.layerOriginX/layerOriginY`，默认取 `View.size` 的一半），
  被调函数内部**不要读全局 `View.size`** 当隐式约定 —— 隐式约定连单测都抓不住（第一版改成读全局时，被 `basis-matches-project` 当场判失败）。

**坑 7：Windows PowerShell 脚本必须是 CRLF 换行**

- **现象**：`tools/input-inject/set-window.ps1` 用纯 LF 保存时，Windows PowerShell 5.1 的
  here-string（`Add-Type @" ... "@`）解析失败，脚本直接报语法错误。
- **正确做法**：`.ps1` 一律 CRLF（写文件时显式用 `\r\n`），并在文件头注释里写明这条。

**坑 8：Lua 5.3+ 没有算术右移 —— `>>` 会直接编译失败**

```ts
// ❌ [FAIL] error TS100026: Signed right shift `>>` is not supported on Lua 5.3+
const r = (hex >> 16) & 0xff;
// ✅ 拆颜色通道用逻辑右移（本项目 2026-09-26 拆 0x36404d 时踩到）
const r = (hex >>> 16) & 0xff;
```

⚠️ 这条属于「**构建会失败**」而不是「运行时报错」—— 一旦忘了看构建合计，提交进去的就是源码与产物不一致的状态（AGENTS.md 的交付纪律）。

### 7.3 结构约定

- 一个文件一个主职责；`Gravity.ts` 保持纯函数、可测。
- 渲染与逻辑分离：物理不读引擎对象，渲染不改物理状态。
- 命名：物理量用 `p/v/a`、行星用 `PlanetDef`、关卡用 `LevelDef`。
- 注释写"为什么"，不写"是什么"。

### 8.2 Web 导出（**本项目最高风险项之一**）

已核实事实：

- Web 构建用 Emscripten 把引擎编译为 WebAssembly，产物是**浏览器端 Web Player**，不是把 Web IDE 搬进浏览器。
- 工具链精确版本：Emscripten `5.0.5`、Rust `1.85.1`（含 `wasm32-unknown-emscripten`）、Go `1.24.3`、Node.js `22.14.0`、CMake `3.30.5`；版本固定在 `Projects/Web/toolchain.env`，不一致会直接报错（仅本地排查可设 `DORA_WEB_ALLOW_TOOLCHAIN_DRIFT=1`）。
- 构建：`Tools/build-scripts/build_web.sh` → 产物在 `result/dora-web-player`。
- 浏览器冒烟：`node Tools/build-scripts/check_web_browser.mjs result/dora-web-player`（截图在 `build/web-browser-smoke.png`）。
- 特性开关：`DORA_WEB_PROFILE`（`core` / `dora-preset` / `custom`）；`DORA_WEB_FEATURE_MUSIC` 与 **`DORA_WEB_FEATURE_MODEL_3D` 默认都是 `OFF`**；启用任一都会构建并链接 Rust 运行时。

> 🔴 **对本项目最关键的一条**：`DORA_WEB_FEATURE_MODEL_3D` **默认为 OFF**。本游戏是 3D 的，Web 导出**必须显式开启 `DORA_WEB_FEATURE_MODEL_3D=ON`** 并重新构建运行时，否则 Web 版本不会有 3D 渲染。
>
> ✅ **实测结果（R1 已关闭）**：**Web IDE 自带的“导出 HTML”可以直接用，且 3D 正常渲染** —— 导出的 HTML 在浏览器中能看到 3 个 3D 物体（球、环、探测器）。这条路径**不需要**从源码编译引擎，也不需要本地装 Emscripten/Rust/Go 工具链。
>
> ⚠️ **但包体积实测 17 MB**（目标 8 MB）→ 见 §11 “R6 缺口分析”。

- **包体积目标**：Web 包 **8 MB 以内**（愿景 §9）。**实测 17 MB（超预算）**，详见 §11 “R6 缺口分析”。
- ⚠️ **手机浏览器待复测**：桌面浏览器已实机跑通；手机端两轮真机问题（触摸命中框只剩左下象限、视口变化未重建）已修

**结论**：任何"做完了"的声明必须写清用的是哪一级证据；没有视觉证据时，明确写 `visual: not_run`。

### 9.1 Agent 侧视觉验证（已落地，解决“Agent 无法看图”）

Agent 无法直接查看图片（`read_file` 拒读二进制、无图像分析工具），但可以用**文本化视觉验证**替代：

- 工具库：`Test/Vision.ts`。
- 原理：`App.saveScreenshot` 输出**未压缩 TGA**（`type=2`，24/32bpp），
  入口是引擎脚本，能用 `Content.load` 读到像素字节，于是可在引擎内解码，
  输出 **ASCII 灰阶图 + 亮度直方图 + 列剖面 + 连通域区域检测**。
- 用法：

```ts
const shotPath = App.saveScreenshot(Path(outDir, 'shot'));
// ⚠️ saveScreenshot 是异步落盘：必须隔几帧再读，否则拿到的是陈旧截图
const report = captureReport(shotPath, [`stats: draws=${view.stats.drawCalls}`]);
Content.save(reportPath, report);
```

- **判定能力（已实测）**：把三个物体放在 x=-6.5 / 0 / +6.5，工具正确输出
  `horizontal segments: 3`，三个 bbox 的 centroid 归一化 x = 0.091 / 0.498 / 0.881，
  与预期位置精确对应。
- **重要局限**：这是**几何/亮度层面**的验证（物体有没有、几个、在哪、多大），
  **不能**替代人类对美观、可读性、手感的判断。它让 Agent 从“盲写”变为
  “能自己确认物体确实渲染且位置正确”，但最终视觉验收仍需人工。
- 同理注意：截图尺寸约 2024×1230×4 ≈ 10 MB，**必须用步长采样**，
  不能把像素物化成 Lua 数组（实测会失败）。

### R6 缺口分析（实测 17 MB vs 目标 8 MB）

**已实测**：Web IDE 导出的 HTML 包体为 **17 MB**（用户实测）。

**预判包体主因**：Web 版把**整个引擎编译成 WASM**（Emscripten），并因 3D 功能链接了 Rust 运行时。游戏自身的代码与资产（3 个 glTF 合计约 8 KB）几乎可忽略。

**可压缩的路径（待验证）**：

1. **压缩传输（成本最低）**：WASM 文本压缩比通常很高（常达 3–4 倍）。17 MB 经 gzip/brotli 后有机会落到 5–6 MB，足以满足“交付包体积”的常见口径（即服务器实际传输字节）。**但需先确认“8 MB”指的是原始体积还是压缩后体积。**
2. **裁剪功能开关**：构建时用 `DORA_WEB_PROFILE=core|custom` 而非 `dora-preset`，关掉用不到的功能（音乐、物理、tilemap 等）→ 需从源码构建，当前环境不具备（见 R1 探测）。
3. **无法从项目侧解决**：包体由引擎运行时主导，减小项目资产对 17 MB 几乎无影响。

**结论**：R6 是**当前唯一已知的验收风险**，且**无法靠代码优化解决**（包体由引擎 WASM 主导）。用户已决定**暂缓**：
提交前若需要，再与活动方确认口径（原始体积 vs 压缩后），或走源码构建裁剪路线。

**裸测最小验证脚本（骨架，`Test/Smoke.ts` 方向）**：参考 `measure-and-debug-3d-scene` 的做法——渲染稳定后取 `view.stats`（`drawCalls`、`visibleVisuals`）并 `App.saveScreenshot(...)`，把 `status=...` 写入标记文件，作为可对比基线。
