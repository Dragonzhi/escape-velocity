## 1. 项目一句话与总目标

**用一次发射，借行星的力，把一枚探测器送出太阳系。**

竖屏、单指触屏、六关的物理规划小游戏。玩家在**发射前**调整方向与力度、观察被引力掰弯的预测轨迹；**松手后不可修正**，只能看着探测器按物理飞出去，最后结算"借力成功 / 错过 / 撞毁"。

交付目标（活动硬性要求，见愿景 §8）：

| 引擎 | Dora SSR |
| 语言 | TypeScript / TSX |
| 形态 | 竖屏，单指触屏，全流程触屏可完成 |
| 导出 | Web (HTML)，并通过运行测试 |
| 开源 | AGPL-3.0-only |
| 仓库 | AtomGit 公开仓库 |

## 3. 技术栈与运行环境

- **引擎**：Dora SSR。游戏运行时由引擎执行；TypeScript 是源码，编译为 Lua 后由引擎执行。
- **入口**：项目根 `init.ts`。
- **模块导入规范**：
  - 引擎 API：`import { ... } from 'Dora';`
  - 本项目模块：斜杠分隔的**项目根相对模块名**，例如 `import { Game } from 'game/Game'` → 解析到 `game/Game.ts`。**不要**写 `./`、`../` 或带 `.ts` 扩展名。
  - 若通过 `requireProjectModule` 加载（测试用），依赖缓存名用点号，例如 `"game.Game"`。
- **不使用**：浏览器 DOM/Canvas、`requestAnimationFrame`、`setTimeout/setInterval`、Node.js 的 `fs/path/process`、npm 包。
- **计时与循环**：`node.schedule((dt) => {...})` 或 `threadLoop`，计时用累加 `dt`。
- **坐标系**：左手系，+X 右、+Y 上。`Director.entry` / `Director.ui` 直接子节点以**屏幕中心**为原点。
- **关键引擎对象（已核实签名）**：

| 对象 | 用途 | 关键成员 |
|---|---|---|
| `Director.entry` | **3D 场景根**（类型为 `View3D`） | `scene`、`stats`、`showAABB`、`shadowMapSize`、`addChild`、`getRayOrigin/getRayDirection/pick`、`setEnvironmentMap`、`setEnvironmentIntensity` |
| `Director.ui` | 2D UI 根（HUD、按钮） | `Node` |
| `Director.pushCamera` | 设置当前相机 | `pushCamera(camera)` |
| `Camera3D` | 3D 相机 | `position`、`target`、`up`、`lookAt(pos, target, up?)` |
| `Node3D` | 3D 节点基类 | `position`、`angleX/Y/Z`、`scaleX/Y/Z`、`addChild`、`convertToWorldSpace` |
| `Model3D(path)` | 从 glTF 加载模型，**返回 `Model3D \| undefined`** | 每个实例独立变换；同路径共享资源 |
| `DirectionalLight3D` | 一盏方向光 | `color: Color3`、`intensity`、`angleX/angleY`、`shadowSoftness` |
| `Surface3D(content, size, pixelSize?)` | 把 2D 节点放进 3D 世界 | `billboard: Billboard.None/Screen/YAxis` |
| `Line` | **2D** 折线（`Vec2[]`） | `set/add/clear`、`depthWrite`、`blendFunc` |
| `DrawNode` | 2D 图元 | `drawDot`、`drawSegment(from,to,radius,color)`（无 `drawRect`，用 `drawPolygon`） |
| `View` | 视图设置 | `size`、`fieldOfView`、`nearPlaneDistance`、`farPlaneDistance`、`postEffect`、`scale` |
| `App` | 应用 | `deltaTime`、`runningTime`、`saveScreenshot(path)` |
| `Content` | 资源/文件 | `save`、`load`、`exist` 等 |

> ⚠️ **注意**：`View3D` 提供的是 **屏幕→世界** 的射线（`getRayOrigin/getRayDirection`），**没有**现成的 **世界→屏幕** 投影。轨迹从 3D 世界投影到 2D 覆盖层需要自建投影（见 §5.5 与 §11 R4）。

## 4. 架构

### 4.1 分层

```
init.ts                 入口：只做装配与启动
  └─ game/Game.ts        顶层状态机 + 主循环（schedule 驱动）
       ├─ game/Level.ts          单关运行时：一个关卡的完整生命周期
       │    ├─ game/Gravity.ts   纯物理：引力积分 + 轨迹预测（可单测，不依赖引擎）
       │    ├─ game/Scene.ts     3D 场景搭建：行星、探测器、光源
       │    ├─ game/CameraRig.ts 相机跟随与拉远
       │    └─ game/Trajectory.ts 轨迹渲染（预测线 + 真实尾迹）
       ├─ game/Hud.ts        触屏 UI：拖动、松手、结算按钮、关卡选择
       └─ game/Config.ts     全局常量、设计尺寸、配色、调参表
```

**分层原则**：

1. `Gravity.ts` 是**纯函数模块**，只依赖数字与 `Vec2`，不碰任何引擎对象 → 可被测试直接调用，也是"预测轨迹 = 真实轨迹"的唯一实现。
2. `Scene/CameraRig/Trajectory` 只负责"把状态画出来"，不改物理状态。
3. `Hud` 只发意图（aimChanged / launchRequested / retry / backToSelect），不直接改游戏状态。
4. `Game` 是唯一持有全局状态机的模块。

### 4.2 模块清单

| 文件 | 职责 | 依赖 | 状态 |
|---|---|---|---|
| `init.ts` | 装配与启动：关卡选择 ⇄ 单关运行时（惰性建关）+ 单一主循环 | 全部 | ✅ S2.3 |
| `game/Config.ts` | 设计尺寸、物理常量、时长、调参 | `Dora` | ✅ S1.4 |
| `game/Gravity.ts` | 引力积分、预测采样、命中判定 | 无（纯逻辑） | ✅ S1.1 |
| `game/LevelData.ts` | 六关配置数据 + 目标判定 | `game/Config` | ✅ S2.1 |
| `game/Level.ts` | **未单独落地**：单关生命周期由 `init.ts` 的 `ensureLevel` + `game/Game` 共同承担 | — | 取消（见下方说明） |
| `game/Scene.ts` | 3D 场景对象 | `Dora`、`LevelData` | ✅ S1.2 |
| `game/CameraRig.ts` | 相机跟随 | `Dora` | ✅ S1.2 |
| `game/Trajectory.ts` | 预测线/尾迹渲染 | `Dora`、`Gravity` | ✅ S1.3 |
| `game/Ui.ts` | **视图空间 2D 原语**：面板 / 居中文字 / 可点按钮（配色与触屏下限集中在此） | `Dora` | ✅ S2.2 |
| `game/Progress.ts` | **解锁进度**：夹紧/推进（纯函数）+ `writablePath` 存档读写 | `Dora` | ✅ S2.3 |
| `game/Hud.ts` | 触屏输入（矄准）+ **结算面板** + **关卡选择** | `Dora`、`game/Ui`、`game/Game` | ✅ S2.3 |
| `game/Game.ts` | 状态机与主循环 | 全部 | ✅ S2.3 |

> **`game/Level.ts` 为什么不建**：分层图里预留的“单关生命周期”最终被两件东西吸收了 ——
> 纯状态机部分在 `game/Game.ts`（`GameCore` + `createGame`），引擎侧“一关一套运行时”的
> 建/切在 `init.ts` 的 `ensureLevel`/`showOnlyLevel`。再抽一层会只剩转发代码。
> `Hud.ts` 同时放“矄准输入”和“面板/关卡选择”，是因为两者共用同一套坐标换算与触屏约定。

### 4.3 顶层状态机

```
Boot → Title(金唱片开场，S3.3) → LevelSelect ⇄ Aiming → Flying → Result → (重试 | LevelSelect)
```

- `LevelSelect`（S2.3 ✅）：六关竖排按钮；已解锁可点、未解锁灰掉且**不可点**。
  **启动即进入本阶段**（Title/金唱片开场属 S3.3，未做）。
  底部提示 `完成一关即解锁下一关`，副标题 `已解锁 N / 6`。
- `Aiming`：全局冻结（D2），玩家拖动，实时更新预测轨迹。
- `Flying`：松手瞬间进入，行星相位从 0 开始，探测器发射；不可输入。
- `Result`：判定 借力成功 / 错过 / 撞毁；结算面板给"重试本关 / 返回关卡选择"（D5）。
  **只有 Result 态能返回关卡选择**（`coreBackToSelect`）：飞行途中不许“撤退”，
  与“松手后不可修正”一致 —— 不可撤销就要走完结算。
- **单一 schedule**：整个游戏只应有一个驱动回调（挂在 `Game` 的根节点上）。不要把更新逻辑分散到多个 `schedule`，同节点二次 `schedule` 会覆盖前者。
  S2.3 的关卡切换仍然是**一个** `threadLoop`：它每帧只驱动“当前激活的那一关”的 `game.update`，
  非激活关卡的 3D 容器 `visible = false`、矄准输入关闭。

#### 4.3.1 解锁制进度（D5，S2.3 ✅）

- 进度只有一个数：`unlocked` = **已解锁的最高关卡索引（0 基）**。`0` = 只开第一关。
- **只有 success 解锁** `levelIndex + 1`；`missed` / `crashed` 不动进度；最后一关通关不越界。
- 重复通关旧关**不回退**（`advanceUnlocked` 取 `max(已解锁, levelIndex+1)`）：
  解锁制只有“解锁”没有“上锁”。
- 存档：`<writablePath>/escape-velocity.progress`，内容**只有一行** `unlocked=N`。
  ⚠️ 可写目录是 `Content.writablePath`（`App` 在 v1.9.3 里**没有**这个成员，已核对 d.ts）。
  实测该路径在 `%APPDATA%/IppClub/DoraSSR/`（**不在项目内**，所以存档不会污染仓库）。
- 文件不存在 / 内容损坏 / 数字非法（`unlocked=abc`、空文件、浮点写法）→ 视为 `0`，**不抛错**。

#### 4.3.2 关卡运行时是**惰性**建的（S2.3 ✅）

- 每关第一次被选中时才建：`Node3D()` 容器 → `addChild(Director.entry)` → `buildScene` →
  相机 / 机架 / 轨迹 / 矄准输入 → `createGame`。
- 切换关卡**只切 `visible`**（3D 容器）与 `aim.setEnabled`（输入层）+ `Director.pushCamera`，
  **不销毁已建节点**：销毁语义在引擎里没有明确文档，而重建 glTF 实例有卡顿风险。
- 每关的 2D 层（轨迹 + 触摸层）**先于 UI 叠层创建**：Dora 按子节点顺序绘制，
  后加的画在上面 —— 否则后建的轨迹线会盖住结算面板。

## 5. 核心系统设计

### 5.1 物理：把 3D 砍成 2D 平面

- 所有引力计算在**一个平面**内完成（黄道面）。行星视为点质量，引力按平方反比。
- 渲染仍是 3D：相机斜看这个平面，行星是球体，轨迹是发光的线。
- ⚠️ **平面→世界的映射方向（已实测确定，R3 关闭）**：物理平面必须映射到屏幕上
  **沿屏幕竖直方向**（即世界 Z 进深），**不能**沿屏幕水平方向（世界 X）。
  原因：竖屏宽高比 0.5625，横向空间只有纵向的 56%。实测同一相机（dist=30/tilt=45）：
  横向轨道的 `maxNdcX=1.50`（被裁），纵向轨道的 `maxNdcX=0.72` / `maxNdcY=0.65`（完整可见）。
  推荐映射：平面 `(u, v)` → 世界 `(0, v, u)`；相机在 +Y/+Z 方向斜俯视，视线指向 -Z。
  映射常量集中在 `Config.ts`。
- **相机倾角安全区间**：tilt 控制在 **20°–60°**（dist=30 时 maxNdcY 为 0.34–0.74）；
  超过 70° 会贴边（maxNdcY ≥ 0.86），80° 基本出界。
- **相机距离**：竖屏下纵向轨道在 `dist ≥ 25` 即可完整框住；横向轨道需 `dist ≥ 50`。
  这正是 D3“动态跟随拉远”必要的量化依据。

加速度：

```
a(p, t) = Σ_i  GM_i * (q_i(t) - p) / |q_i(t) - p|^3
```

- `q_i(t)` = 行星 i 在时刻 t 的位置（公转，D1）。
- `GM_i` 用"一个数字"表示引力强度，不必对应真实天体质量。
- **不进黑洞**：`|q_i - p|` 小于行星半径 → 判定撞毁，停止积分（见 §5.8）。

积分：**固定时间步**（固定 dt，例如 1/120 秒），半隐式欧拉或 velocity-Verlet。

- 固定步长的意义：**同一个输入每次结果一致**（验收要求"可预测、可学习"）。
- 帧的 `dt` 只用于"推进多少个物理步"，不让物理步长随帧率变化。必要时对一帧最多推进的步数设上限，防止卡顿后跳帧。

### 5.2 引力弹弓（D1 · A 方案）

- 行星在**公转**。引力场随行星移动，探测器从行星**后方**掠过时自然获得净加速，从**前方**掠过自然减速。这是真实弹弓的机制，不需要额外规则。
- **可视化教学**：在行星上画"公转方向箭头 / 尾迹"，让玩家看见"该从哪边抄"。
- 手感调参在 `Config.ts`：行星公转速度要"肉眼可见但不夸张"，`GM_i` 要能产生明显弯曲但仍可规划。
- **原理提示（给玩家的一句话）**：从行星运行方向的**后方**掠过 → 加速；从**前方**掠过 → 减速；越近效果越强，太近撞毁。

### 5.3 时间模型（D2）

- `Aiming`：物理时间冻结，行星固定在 `phase0`。
- 松手瞬间：
  1. 行星相位归零（`phase = 0`，即用 `phase0` 作为 t=0 姿态）；
  2. 探测器以玩家设定的发射向量出发；
  3. 物理时间开始推进，行星按周期公转。
- **预测轨迹与真实轨迹共用 `Gravity.ts`**：预测 = 从当前发射向量出发、用同一积分器推演出 N 步。因此"预测线看见的"就是"松手后发生的"（在固定步长下应完全一致）。

### 5.4 相机（D3）

- 单一 `Camera3D`，每帧（`Aiming` 与 `Flying` 都）重算：
  - `target` = 探测器与目标星位置的加权中点；
  - `position` = `target` 沿固定俯视方向后移 `distance`；
  - `distance` 随"探测器到目标的距离"单调增长，并设最小/最大值夹紧。
- 俯视角固定（如从上后方 35°–55°），保证"从行星后方/前方掠过"在屏幕上可读。
- **竖屏适配**：见 §5.9，视野/投影要保证纵向能装下整条轨道。
- 拉远要**平滑**（对 distance 做一阶滤波），避免抖动。

### 5.5 轨迹渲染（最关键的视觉元素）

需求：一条发光的曲线，且**实时**随拖动重画。

已确认的约束：

- `Line` 是 **2D** 折线（`Vec2[]`），不能直接放进 3D 世界画 3D 折线。
- `View3D` **没有** world→screen 投影 API。

**方案（已实测标定并固化）**：

**主方案：2D 覆盖层 + 自建投影（已验证，R4 已关闭）**

Dora 的 `Camera3D` 没有暴露投影矩阵，但 `View3D` 提供了 `getRayDirection(viewPoint)`。
用"对已知世界点搜索射线方向点积最大的屏幕位置"作为真值，实测确定了：

| 项 | 实测结论 |
|---|---|
| `viewPoint` 坐标空间 | **像素坐标，原点在左上角**：`x ∈ [0, W]`、`y ∈ [0, H]`（+Y 向下） |
| 相机手性 | `right = cross(forward, up)` |
| 视野 | `View.fieldOfView` 是**垂直** FOV（度）；`focal = 1 / tan(fovY/2)` |
| 投影公式 | `ndc = (v/focal⁻¹...)` 见下 |

```
f = normalize(target - eye)
r = normalize(cross(f, up))      // 手性：注意不是 cross(up, f)
u = cross(r, f)
vz = dot(p - eye, f)
ndcX = (dot(p-eye, r) / vz) * focal / aspect
ndcY = (dot(p-eye, u) / vz) * focal
viewPoint = (W/2 + ndcX * W/2, H/2 + ndcY * H/2)
```

- 实现：`game/Projection.ts`（纯函数，无引擎依赖）。
- 标定与回归测试：`Test/ProjectionProbe.ts`。
- **实测精度**：最大像素误差 **1.00 px**（2024×1230）→ 关闭 R4。
- 🚨 **重要修正（S2 阶段实测发现）**：`getRayDirection` 的 viewPoint 是
  **左下角原点、+Y 向上**（不是早期误判的“左上角 +Y 向下”）。标定时的
  中心点检验对 Y 翻转不敏感，所以当时未发现；后经**颜色标记球对照渲染位置**
  才定位（绿=探测器、红=火星、白=注视点标记球——白球精确渲染在窗口中心，
  而另两球与 project() 输出恰好关于屏幕中心**上下镜像**）。
  ⇒ **`project()` 的输出已是中心原点 +Y 向上，与 Dora UI 空间一致，
  `toOverlay()` 是恒等变换**。旧版多翻一次，导致所有 2D 覆盖层（预测线）
  垂直镜像于真实渲染 —— 玩家看到的就是“预测线不从探测器出发”。
- **屏幕方向语义（修正后）**：世界 +z（靠近相机侧）在屏幕**下方**，
  远离相机（-z）在**上方** —— 与真实相机一致（近景在画面下方）。
  游戏中探测器在屏幕下方、目标在上方，向上发射。

**发光效果**：高亮色 + `blendFunc` 叠加 + 略粗的 `drawSegment`。
**预测线与真实尾迹必须用同一套采样数据**，避免"看起来一样、其实不一样"。

**✅ 已落地实现（`game/Trajectory.ts`，S1.3 已验证）与两个实测坑**：

1. ⚠️ **轨迹必须挂在 `Director.ui`，不能挂 `Director.entry`**。
   `Director.entry` 是 **`View3D`**（3D 视图根），不能承载 2D 绘制节点。
2. ⚠️ **用 `DrawNode.drawSegment`，不要用 `Line`**。
   `Line` 的线宽**不可控**（约 1px），在 2024×1230 下几乎不可见。
   实测：改用 `DrawNode` 后，区域检测从 **11 个 → 40+ 个**，亮像素占比 **0.07% → 0.30%**。
   圆头效果靠“每段 `drawSegment` + 每个顶点补一个 `drawDot`”。
3. **性能**：逐段绘制开销大，靠 `decimate(points, maxPoints)` 均匀抽稀（保留首尾）控制段数。
4. **投影预计算**：每帧要投影数百个点，用 `prepareCamera()` 算一次相机基，
   再用 `projectPrepared()` 逐个投影（避免重复算 f/r/u/focal）。
5. ⚠️ **`Vec2` 是 float32**（引擎 C++ 类型）。与 float64 普通对象比较会有 ~1e-8 相对误差；
   写断言时应把两边都降为 float32 再逐位比较，而不是用绝对容差。
6. 🚨 **预测线必须每帧重画**（不能只在拖动时重画）：重试后相机会用 lerp 从飞行终点
   视图滑回矄准视图（约 20-30 帧）；若只在拖动时画一次，线会冻结在过渡中途的投影上，
   看起来“不是从探测器出发”。（注：这是一起真实 bug，与上一条镜像 bug 独立。）

### 5.7 输入与交互

- 单指拖拽。实现用节点触摸回调：设置 `node.touchEnabled = true` 后使用 `onTapBegan / onTapMoved / onTapEnded`（`touch.location` 是**接收节点局部坐标**；`touch.viewLocation` 是视图逻辑坐标）。
- 拖拽语义（在 `Aiming`）—— **2026-09-24 按用户真机反馈改为相对拖动（虚拟摇杆）**：
  - **按下点 = 摇杆零点**：按下瞬间瞄准归零到"直飞"（正对目标、最小力度），预测线立刻显示中性方向；
  - 之后的**位移**（相对按下点）决定方向与力度：位移方向 = 发射方向（屏幕上 = 直飞，右 = 右偏），
    位移长度 = 力度（夹紧到 min/max）⇒ **按在哪里都能瞄**；
  - 拖动过程中**每帧重算并重画预测轨迹**；
  - 抬起 = 松手 = 发射（不可撤销，愿景 §3/§15）。
  - 旧模型（"探测器位置 → 触摸点"的绝对方向，按下即按距离给力度）已废弃：真机上按下位置与探测器位置
    无关联，玩家一按就拿到了力度、方向也由按下点决定，与手感预期不符（用户反馈"按下的地方也不是飞行器所在的地方"）。
- UI 按钮（结算、关卡选择）必须是**可见可点**的 2D 按钮（触屏目标足够大，竖屏下拇指可达）。
- 全流程必须触屏可完成（开始 → 游玩 → 结算 → 重开）。

**✅ 已落地实现（`game/Hud.ts`，S1.4 已验证）与关键实现要点**：

1. **统一坐标空间为“投影偏移空间”**（中心原点、**+Y 向上**，即 `project()` 的输出空间）。
   探测器屏幕位置直接来自 `project()`，触摸位置经 `localToOffset()` 换算：
   `offset.x = local.x - W/2`，`offset.y = local.y - H/2`
   （全屏节点局部坐标是**左下原点、+Y 向上**，两个空间同向，只差中心平移）。
   ⚠️ 修正后：平面 y 轴与偏移 y 轴**反向**（平面 -y = 朝目标 = 屏幕上方），
   所以瞄准方向必须取 `uy = -dy / len`（S2 修投影镜像时曾误删此负号，被 HudTest 当场抓回）。
   ⚠️ 初版把“`project()` 输出”与“触摸换算”当成同一空间直接相减 —— 当时两者反向，方向会算错。
2. **触摸层必须是一个带尺寸的全屏节点**（`size = View.size`、`anchor = (0.5,0.5)`），
   否则 `touch.location` 的局部坐标没有明确范围，换算无从谈起。
3. **`Touch` 是私有构造，无法程序化注入** → 真实触摸的坐标系需一次人工校对；
   `localToOffset()` 是唯一校准点。`handleLocal` / `handleOffset` 是为
   键盘降级/回放/无头测试保留的输入缝隙。
4. **接口用属性式箭头函数类型**，且返回对象里不要用简写属性引用局部函数
   （会触发 TS100016 “无 this 转换”错误，包一层箭头函数即可）。
5. 调参：`AimMinSpeed=2` / `AimMaxSpeed=22` / `AimMaxDragPx=380`（`Config.ts`）。

**✅ S2.2/S2.3 的 UI 追加要点（结算面板 · 关卡选择）**：

6. **2D 原语集中在 `game/Ui.ts`**：`createPanel`（实心矩形，`DrawNode.drawPolygon` 四顶点）/
   `createLabel`（居中锚点文字）/ `createButton`（**自身即可点节点**：底色 + 居中 Label +
   `touchEnabled`/`swallowTouches`/`onTapEnded`，按下换底色）。字体名、配色、触屏下限都只在这个文件里改。
   颜色用 `0xRRGGBB` + 单独 alpha；取通道用除法而不用 `>>`/`&`（位运算在 TSTL 各 Lua 目标上支持面更窄）。
7. **锚点统一 `(0,0)`、局部绘制 `[0,w]×[0,h]`**：d.ts **没有**写明 `anchor`/`size` 与
   “子节点坐标系 / 触摸命中矩形”的关系（纯 `Node` 与 `Sprite` 的实现允许不同）。
   `anchor = 0` 时两种解释重合 ⇒ 画出来的矩形与命中矩形必然一致；代价是按**左下角**摆放。
   面板内部因此天然是 `[0,W]×[0,H]`、左下原点、+Y 向上的坐标系，与矄准层同向，少一次心算。
8. 🚨 **每个全屏触摸层都要随“是否在玩这一关”开关 `touchEnabled`**（S2.3 实测发现的坑）：
   `swallowTouches = true` 的层会**独占**它收到的触摸。多关并存时，上一关的矄准层若还开着，
   屏幕上的点击全被它吞掉，第二关表现为“怎么拖都没反应”。
   `AimInput.setEnabled` 现在同时改内部开关与 `touchLayer.touchEnabled`。
   ⚠️ `onTapBegan`/`onTapMoved`/`onTapEnded` 注册时会把 `touchEnabled` 置回 true，
   所以“初始关闭”必须写在**注册之后**。
9. **按钮不做坐标过滤**：Dora 没有“触摸取消”回调 —— 按下后划出按钮再松开，`onTapEnded` 仍会触发。
   这里选择“多触发一次”，而不是用 `touch.location` 判定是否松开在按钮内：
   `Touch` 是私有构造，无头环境无法标定它的局部空间，空间假设错了会让按钮**整块点不到**。
10. **触屏目标尺寸：按可用空间算，绝对下限只保"地板"**（2026-09-24 竖屏实测修正）：
    - 竖屏窄屏实测（`View.size = 601×1066`，来自 400×710 客户区）时，旧写法"高 ≥ 130 / 宽 ≥ 560"**直接溢出**：
      6 行 ×130 + 5×18 间距 = 870 > 可用 636 ⇒ **L6 被裁一半、底部提示整条被挤出屏外**；
      结算卡片宽只有 529，而按钮写死 ≥560 ⇒ **按钮横向戳出卡片外**（两处都有截图证据）。
    - 现规则：列数随宽高比**自适应**（竖屏 **2 列×3 行**、横屏 1 列×6 行）；按钮尺寸由可用空间推算
      （`availW`/`availH`）；绝对下限降到 `MinButtonWidth=160 / MinButtonHeight=72`（只防"小到点不中"）；
      结算按钮宽 = 卡片宽 − 60，卡片若高于屏幕则先压按钮高度。
    - 全部按 `View.size` **实际逻辑像素**推导，不按设计分辨率换算 ⇒ **设计分辨率（1080×1920）不再是约束**。
    实测两套截图均已通过：竖屏 601×1066（三态）、横屏 2024×1231（三态）。
13. **`View.size` = 窗口客户区像素 × 1.5**（引擎渲染尺寸；实测 400×710 客户区 → 601×1066）。
    代码只读 `View.size`，不要读窗口/客户区尺寸，也不要对这个系数做任何假设（不同平台/缩放会变）。
11. **`Label()` 可能返回 undefined**（字体缺失）：`Ui.ts` 的 `setLabelText/setLabelColor/setLabelCenter`
    一律容忍 undefined，调用点不必到处写 `if`。
12. **局部函数不要直接赋给“成员函数式”的属性**：会触发 TS100016
    （`{ onRetry: onRetryTap }` ❌ → `{ onRetry: () => onRetryTap() }` ✅），与手册 §7.2.1 同源。

## 7. 编码规范

### 7.1 Dora/TS 硬规则

- **禁止** `any`。用具体类型、`unknown` + 收窄、泛型或精确联合。
- **禁止**裸 `null`。用 `undefined` / 省略字段（Lua 语义）。
- **工厂命名空间是值不是类型**：实例标注用 `Vec2.Type`、`Color.Type`、`Camera3D.Type` 等，不要写 `ReturnType<typeof X>`。
- **不支持** `Math.hypot`、`Math.imul`。用 `Math.sqrt(x*x + y*y)` 与普通算术。
- **可选返回值必须收窄**：如 `Model3D(...)` 返回 `Model3D | undefined`，`Label(...)` 可能返回 `undefined`。先用 `if (!x) throw ...` 或分支处理，再使用。
- **Lua 数组不能表示 `undefined` 元素**：不要用可选工厂结果直接拼数组。
- 缩进用**普通空格**，绝不出现字面 `\t` 两个字符。

### 7.2 TSTL（TS→Lua）坑（来自 `caveats.md`）

| 项 | 差异 | 规避 |
|---|---|---|
| 布尔真值 | `0`、`""`、`NaN` 在 Lua 中为**真** | 只用显式布尔表达式 |
| `==` / `===` | TSTL 中等价 | 无需纠结，但保持严格写法 |
| `null` / `undefined` | 都变 `nil` | 避免 `null` |
| 表键存在性 | 赋 `nil` 即删键 | 用哨兵值 `-1` 或自定义 `Null = {}` |
| 数组长度 | `.length` → `#`，中间空洞会出错 | 不要写中间为 `undefined` 的数组 |
| 迭代顺序 | 无序 | 需要顺序就用数组 |
| 局部变量上限 | Lua 局部变量 200 个 | 大函数拆小；必要时合并导出表 |
| **对象成员函数的 self** | 启用了 `noImplicitSelf`，但**对象/接口的成员函数依然默认带 self**，生成 `obj:method(arg)` 冒号调用 | 给 interface 加 `/** @noSelf **/`，或每个方法写 `this: void` |
| **工厂命名空间不能当类型** | `Vec3` / `Node3D` / `Color` 等是**值**，不是类型 | 标注用 `Vec3.Type` / `Node3D.Type` / `Color.Type` |

#### 7.2.1 两个已实际踩到的坑（写代码时必须避开）

**坑 1：对象成员函数默认带 self（会造成参数错位）**

```ts
// ❌ 错误：TSTL 生成 `scene:syncProbe(pos)`，
//    scene 会变成第一个参数，函数体内的 p 收到的是 scene → 报 “field 'x' is nil”
interface GameScene {
	syncProbe(p: P2): void;
}

// ✅ 正确：加 @noSelf，生成点调用 `scene.syncProbe(pos)`
/** @noSelf **/
interface GameScene {
	syncProbe(p: P2): void;
}

// ✅ 也可逐个方法声明
interface GameScene {
	syncProbe(this: void, p: P2): void;
}
```

⚠️ 注意：**用属性式函数类型（`syncProbe: (p: P2) => void`）不能解决这个问题**，仍会被当作成员函数。
这个错误编译期**不报错**，只在运行时莫名奇妙地报 “nil 值算术”—— 极难定位。

**坑 2：`threadLoop` 的返回值语义易搞反**

```ts
// threadLoop 回调：返回 false 继续，返回 true 停止
// ❌ return frame < 600;   → frame=1 时返回 true，循环立即停止（看起来像“卡住”）
// ✅ return frame >= 600;  → 正确
```

**坑 3：`App.saveScreenshot` 是异步落盘**

请求后**不能立即读**，会拿到**上一次的陈旧截图**（图像与上一次逐字节相同，极具迷惑性）。
正确做法：请求 → 隔几帧 → 读取。详见 §9.1。

**坑 4：不要用 `toExponential`**

TSTL 不支持 `Number.prototype.toExponential`。用 `toFixed` 代替。

### 7.3 结构约定

- 一个文件一个主职责；`Gravity.ts` 保持纯函数、可测。
- 渲染与逻辑分离：物理不读引擎对象，渲染不改物理状态。
- 命名：物理量用 `p/v/a`、行星用 `PlanetDef`、关卡用 `LevelDef`。
- 注释写"为什么"，不写"是什么"。

### 8.2 Web 导出（**本项目最高风险项之一**）

已核实事实：

- Web 构建用 Emscripten 把引擎编译为 WebAssembly，产物是**浏览器端 Web Player**，不是把 Web IDE 搬进浏览器。
- 工具链精确版本：Emscripten `5.0.5`、Rust `1.85.1`（含 `wasm32-unknown-emscripten`）、Go `1.24.3`、Node.js `22.14.0`、CMake `3.30.5`；版本固定在 `Projects/Web/toolchain.env`，不一致会直接报错（仅本地排查可设 `DORA_WEB_ALLOW_TOOLCHAIN_DRIFT=1`）。
- 构建：`Tools/build-scripts/build_web.sh` → 产物在 `result/dora-web-player`。
- 浏览器冒烟：`node Tools/build-scripts/check_web_browser.mjs result/dora-web-player`（截图在 `build/web-browser-smoke.png`）。
- 特性开关：`DORA_WEB_PROFILE`（`core` / `dora-preset` / `custom`）；`DORA_WEB_FEATURE_MUSIC` 与 **`DORA_WEB_FEATURE_MODEL_3D` 默认都是 `OFF`**；启用任一都会构建并链接 Rust 运行时。

> 🔴 **对本项目最关键的一条**：`DORA_WEB_FEATURE_MODEL_3D` **默认为 OFF**。本游戏是 3D 的，Web 导出**必须显式开启 `DORA_WEB_FEATURE_MODEL_3D=ON`** 并重新构建运行时，否则 Web 版本不会有 3D 渲染。
>
> ✅ **实测结果（R1 已关闭）**：**Web IDE 自带的“导出 HTML”可以直接用，且 3D 正常渲染** —— 导出的 HTML 在浏览器中能看到 3 个 3D 物体（球、环、探测器）。这条路径**不需要**从源码编译引擎，也不需要本地装 Emscripten/Rust/Go 工具链。
>
> ⚠️ **但包体积实测 17 MB**（目标 8 MB）→ 见 §11 “R6 缺口分析”。

- **包体积目标**：Web 包 **8 MB 以内**（愿景 §9）。**实测 17 MB（超预算）**，详见 §11 “R6 缺口分析”。

## 9. 验收标准与证据分级

愿景 §15 的验收清单，逐条配上**证据类型**。注意：证据类型不能互相替代。

| 验收项 | 需要的证据类型 | 当前状态 |
|---|---|---|
| 六关全部可通关，每关一个新决策 | 运行时可玩 + 人工/视觉验收 | 未开始 |
| 全流程触屏可完成（开始→游玩→结算→重开） | 运行时可玩 + 触屏人工验收 | 未开始 |
| 松手后不可修正 | 状态机行为验证（输入被忽略） | 未开始 |
| 同一输入结果一致 | `Gravity.ts` 确定性单测（纯函数） | 未开始 |
| Web 导出后浏览器可完整游玩 | Web 构建成功 + 浏览器实机运行 | 未开始 |
| 手机触控缩放正常、按钮可见可点 | 真机/模拟器人工验收 | 未开始 |
| 60 秒内讲清玩法 | 演示视频脚本 | 未开始 |
| Web 包体积在预算内 | 构建产物实际大小 | 未开始 |

**证据分级（务必区分）**：

1. `build` 通过 = 源码能编译。**不等于**功能正确。
2. 运行时存活（`running = true`）= 没崩。**不等于**画面正确、玩法成立。
3. 确定性单测通过 = 逻辑符合断言。**不等于**视觉/手感达标。
4. 人工交互与视觉检查 = 唯一能证明"看得见、点得到、玩得动"的证据。
5. 视觉验收工具可用时，必须检查**初始帧**与**触发主要输入后的帧**，确认 playfield / 玩家对象 / 危险与目标 / HUD / 覆盖层的层级关系。

**结论**：任何"做完了"的声明必须写清用的是哪一级证据；没有视觉证据时，明确写 `visual: not_run`。

### 9.1 Agent 侧视觉验证（已落地，解决“Agent 无法看图”）

Agent 无法直接查看图片（`read_file` 拒读二进制、无图像分析工具），但可以用**文本化视觉验证**替代：

- 工具库：`Test/Vision.ts`。
- 原理：`App.saveScreenshot` 输出**未压缩 TGA**（`type=2`，24/32bpp），
  入口是引擎脚本，能用 `Content.load` 读到像素字节，于是可在引擎内解码，
  输出 **ASCII 灰阶图 + 亮度直方图 + 列剖面 + 连通域区域检测**。
- 用法：

```ts
const shotPath = App.saveScreenshot(Path(outDir, 'shot'));
// ⚠️ saveScreenshot 是异步落盘：必须隔几帧再读，否则拿到的是陈旧截图
const report = captureReport(shotPath, [`stats: draws=${view.stats.drawCalls}`]);
Content.save(reportPath, report);
```

- **判定能力（已实测）**：把三个物体放在 x=-6.5 / 0 / +6.5，工具正确输出
  `horizontal segments: 3`，三个 bbox 的 centroid 归一化 x = 0.091 / 0.498 / 0.881，
  与预期位置精确对应。
- **重要局限**：这是**几何/亮度层面**的验证（物体有没有、几个、在哪、多大），
  **不能**替代人类对美观、可读性、手感的判断。它让 Agent 从“盲写”变为
  “能自己确认物体确实渲染且位置正确”，但最终视觉验收仍需人工。
- 同理注意：截图尺寸约 2024×1230×4 ≈ 10 MB，**必须用步长采样**，
  不能把像素物化成 Lua 数组（实测会失败）。

### R6 缺口分析（实测 17 MB vs 目标 8 MB）

**已实测**：Web IDE 导出的 HTML 包体为 **17 MB**（用户实测）。

**预判包体主因**：Web 版把**整个引擎编译成 WASM**（Emscripten），并因 3D 功能链接了 Rust 运行时。游戏自身的代码与资产（3 个 glTF 合计约 8 KB）几乎可忽略。

**可压缩的路径（待验证）**：

1. **压缩传输（成本最低）**：WASM 文本压缩比通常很高（常达 3–4 倍）。17 MB 经 gzip/brotli 后有机会落到 5–6 MB，足以满足“交付包体积”的常见口径（即服务器实际传输字节）。**但需先确认“8 MB”指的是原始体积还是压缩后体积。**
2. **裁剪功能开关**：构建时用 `DORA_WEB_PROFILE=core|custom` 而非 `dora-preset`，关掉用不到的功能（音乐、物理、tilemap 等）→ 需从源码构建，当前环境不具备（见 R1 探测）。
3. **无法从项目侧解决**：包体由引擎运行时主导，减小项目资产对 17 MB 几乎无影响。

**结论**：R6 是**当前唯一已知的验收风险**，且**无法靠代码优化解决**。需在提交前与活动方确认口径，或走源码构建裁剪路线。
| R7 | 后处理（引力透镜） | 最后两天才试 | 能出且不掉帧 | 直接砍（愿景 §13 第 4 级） |

**裸测最小验证脚本（骨架，`Test/Smoke.ts` 方向）**：参考 `measure-and-debug-3d-scene` 的做法——渲染稳定后取 `view.stats`（`drawCalls`、`visibleVisuals`）并 `App.saveScreenshot(...)`，把 `status=...` 写入标记文件，作为可对比基线。
